# «Пульс» — персональные требования и возможности бизнеса в MAX

«Пульс» помогает предпринимателю не пропускать применимые к нему изменения. Сервис строит профиль компании по ИНН, сопоставляет его с правилами и мерами поддержки и присылает в MAX короткие уведомления со ссылкой на официальный первоисточник.

Продукт не заменяет юриста или бухгалтера, не рекомендует действия и не выдаёт модельные данные за официальные.

## Статус проекта

Идёт сборка MVP для хакатона MAX (кейс «Эффективный бизнес»). Этот README описывает **текущее состояние `main`**. Финальная сверка README выполняется после демо-триггера (K-29) и боевого прогона в MAX (K-30d).

Уже в `main`:

- доменная модель, контракты v1 (`contracts/`) и хранилище PostgreSQL с миграциями;
- вычисление применимости: условия, пять статусов, цепочка объяснения (`packages/rules`);
- сервисы перечня, профиля и пересчёта (`packages/services`);
- источник профиля из реестра МСП и модельный источник (`packages/adapters`);
- пакеты правил: общепит (федеральный, дополнение «Татарстан», возможности) и автосервис;
- фоновые задачи: загрузка ленты regulation.gov.ru, планировщик уведомлений, политика частоты, очередь и отправка в MAX (`apps/worker`);
- транспорт бота (webhook MAX), машина состояний диалога и шаблоны сообщений (`apps/bot`);
- развёртывание на VPS с HTTPS, мониторингом, резервными копиями и SLA пилота.

Ещё не собрано: сценарии бота (онбординг, перечень, настройки), контур диалога, демо-триггер, API и экраны мини-приложения. Точки входа `apps/bot/src/main.ts` и `apps/miniapp-api/src/main.ts` пока пустые, поэтому локальный запуск поднимает инфраструктуру, но не пользовательский сценарий. План и статусы потоков — в [дорожной карте](docs/roadmap.md).

## Сценарий MVP

1. Пользователь открывает бота и вводит ИНН.
2. Сервис находит компанию в реестре МСП и предлагает подтвердить профиль: регион, ОКВЭД, категорию и численность.
3. Движок применимости относит каждое требование пакета к одному из пяти статусов: применяется / не применяется / недостаточно данных / требуется проверка / вне покрытия.
4. При «недостаточно данных» бот задаёт только те уточняющие вопросы, которые меняют результат.
5. При изменении правил пользователь получает уведомление: что изменилось, почему это касается его компании, ссылка на первоисточник и пометка об автоматической обработке.
6. Для проверки изменение показывается видимой кнопкой «🧪 Показать пример изменения (модельное)».

Основной сценарий, включая демо-изменение, проходится в боте. Мини-приложение показывает подробности и настройки и не является обязательным для проверки.

## Архитектура

```text
MAX ──webhook──► apps/bot ─────────────► packages/services ──► packages/rules
                  │  диалог, шаблоны           │                   (применимость)
                  │                            ▼
MAX Mini App ──► apps/miniapp-api ──────► packages/storage ──► PostgreSQL
                                               ▲
apps/worker ───────────────────────────────────┘
  ├─ лента regulation.gov.ru → события изменений
  ├─ планировщик → политика частоты → очередь ──► MAX Bot API
  └─ классификатор: template | GigaChat | локальная модель

packages/adapters ── реестр МСП ФНС, модельные источники
```

| Компонент | Назначение |
| --- | --- |
| `apps/bot` | приём событий MAX, диалог, шаблоны сообщений |
| `apps/miniapp-api` | внутренний API мини-приложения |
| `apps/miniapp` | мини-приложение MAX (React) |
| `apps/worker` | загрузка документов, планировщик уведомлений, отправка |
| `packages/domain` | доменная модель, порты, справочники |
| `packages/rules` | условия, статусы, объяснение, загрузка пакетов правил |
| `packages/services` | перечень, профиль, пересчёт |
| `packages/adapters` | источники профиля, требований, мер поддержки: real, fixture, synthetic |
| `packages/classifier` | провайдеры ИИ и классификатор документов |
| `packages/storage` | схема PostgreSQL, миграции, репозитории |
| `packages/observability` | ошибки, логи без ПДн, проверки здоровья |
| `packages/security` | подпись `initData`, секреты, минимизация ПДн |
| `packages/metrics` | метрики продукта |
| `contracts/` | JSON Schema контрактов v1 и примеры |
| `data/` | пакеты правил и фикстуры |

Подробности: [архитектура](docs/architecture.md) и [ADR](docs/decisions/README.md).

## Требования

- Git;
- Docker с Compose v2 — рекомендуемый способ запуска;
- либо Node.js 24 и pnpm 11 (версия задана в `package.json`, включается `corepack enable`).

## Быстрый локальный запуск

Из чистого клона:

```bash
git clone https://github.com/Diminikhui/max_hackathon.git
cd max_hackathon
cp .env.example .env
docker compose up --build --wait
```

Пустые значения в `.env` заменяются локальными значениями по умолчанию из `compose.yaml`. После запуска:

| Сервис | Адрес по умолчанию |
| --- | --- |
| Мини-приложение | <http://localhost:4173> |
| API мини-приложения | <http://localhost:3000> |
| PostgreSQL | только внутри сети Compose, порт `5432` |
| bot, worker | внешних портов нет |

Порты на хосте меняются через `MINIAPP_PORT` и `MINIAPP_API_PORT`.

### Локально события MAX не принимаются

Compose запускает бота с пустым `MAX_BOT_TOKEN` и `MAX_EVENTS_ENABLED=false`, поэтому локальный контур не получает события выданного бота и не конфликтует с сервером. Токен хранится только на VPS ([ADR-0003](docs/decisions/0003-issued-bot-and-hackathon-contour.md)).

### Запуск без Docker

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm build
pnpm test
```

Проверки перед Pull Request:

```bash
pnpm lint
pnpm typecheck
./scripts/verify-repository.sh
```

Тесты хранилища используют PGlite (PostgreSQL в WASM) и внешней базы не требуют. Очистка сборки — `pnpm run clean`.

## Переменные окружения

Безопасный шаблон — [.env.example](.env.example): значения пустые, реальные токены в репозиторий не попадают.

| Переменная | Назначение | Локально |
| --- | --- | --- |
| `DATABASE_URL` | подключение к PostgreSQL | задаётся Compose |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | локальная база | значения по умолчанию из Compose |
| `MINIAPP_PORT`, `MINIAPP_API_PORT` | порты на хосте | `4173`, `3000` |
| `MAX_BOT_TOKEN` | токен выданного бота | пусто; только на VPS |
| `MAX_API_BASE_URL` | адрес Bot API (хакатонный контур) | `https://platform-api2.max.ru` |
| `MAX_CA_CERT_PATH`, `MAX_CA_CERT_SHA256` | корневой сертификат НУЦ Минцифры и его отпечаток | нужен только для обращений к MAX |
| `MAX_EVENTS_ENABLED` | приём событий MAX | задаётся Compose: `false` |
| `LLM_PROVIDER` | `template`, `gigachat` или `local` | `template` |
| `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE` | доступ к GigaChat | не нужны для `template` |
| `LOCAL_LLM_URL`, `LOCAL_LLM_IMAGE` | локальная модель | необязательно |
| `RULEPACK_DIRECTORY` | каталог установленных пакетов правил | по умолчанию `data/rulepacks/installed` |
| `BACKUP_DIR`, `BACKUP_KEEP`, `BACKUP_MAX_AGE_HOURS` | резервные копии на VPS | локально не используются |
| `MSP_LIVE_INN` | ИНН для ручной живой проверки адаптера МСП | только локально, не коммитить |

Не коммитьте `.env`, токены, пароли и ключи. Проверка TLS не отключается.

## Источник профиля предприятия

Порядок источников ([ADR-0006](docs/decisions/0006-adopted-gap-proposals.md), п. 7):

1. **Реестр МСП ФНС** — основной ([`MspProfileSource`](packages/adapters/src/profile/msp/README.md)). Одним запросом по ИНН даёт основной ОКВЭД, регион, категорию МСП, численность и признак лицензий. Все факты помечены как официальные, с источником и датой.
2. **ЕГРЮЛ/ЕГРИП** — запасной, в работе (K-12a).
3. **Модельный источник** — фикстуры K-28 для тестов и демо, помечены `isModel`.

Ограничения реестра МСП:

- используется внутренний интерфейс страницы поиска `rmsp.nalog.ru` без спецификации: формат может измениться, тогда адаптер отвечает «источник недоступен», а не ломает сценарий. Допустимость такого интерфейса по условиям кейса — открытый вопрос организаторам;
- отклик нестабилен: таймаут 20 с и один повтор, частый опрос не допускается;
- в реестре только субъекты МСП; исключённые из реестра компании считаются ненайденными;
- это срез: реестр обновляется 10-го числа, численность — за прошлый год или ранее;
- дополнительных ОКВЭД ответ не содержит, отсутствие работников из нуля не выводится — бот уточняет у пользователя;
- пользователь подтверждает профиль и может его исправить; ИНН и название ИП не пишутся в логи.

Подробнее: [исследование реестров МСП](docs/research/k04b-msp-registers.md), [требования безопасности](docs/security.md).

## Правила и данные

Пакет правил — данные, а не код: регион и направление подключаются новым пакетом. Каждая запись содержит условие применимости, покрытие, срок и хотя бы одно основание со ссылкой на официальный акт. Статус применимости выводится воспроизводимо из правил и подтверждённых фактов: ИИ его не определяет, а только помогает классифицировать документы ленты и переформулировать готовое объяснение.

| Каталог | Содержимое |
| --- | --- |
| `data/rulepacks/a/` | общепит: федеральный пакет, дополнение «Татарстан», возможности |
| `data/rulepacks/b/` | автосервис: федеральный пакет |
| `data/rulepacks/_golden/` | эталонный перечень для оценки качества |
| `data/rulepacks/_demo-scale/` | модельная демонстрация тиражирования на новый регион и направление |
| `data/fixtures/` | модельные компании и пакеты K-28, записанные ответы источников |

Всё модельное помечено в данных, интерфейсе и сообщениях. Фикстуры K-28 описаны в [README набора](data/fixtures/k28-README.md).

## Демо-триггер

В разработке: K-29 ([#214](https://github.com/Diminikhui/max_hackathon/issues/214)). Проверка занимает 10–15 минут, и за это время ни одно правило не изменится, поэтому изменение показывается отдельной кнопкой:

- видимая кнопка бота **«🧪 Показать пример изменения (модельное)»**;
- берётся заранее подготовленная следующая версия модельного пакета, например `k28-rulepack-v2` поверх v1 с новой записью `k28.water-marking`;
- запускается тот же механизм, что при реальном изменении: новая версия пакета → планировщик → пересчёт → уведомление (контур K-30a);
- уведомление самодостаточно: что изменилось, почему касается компании, ссылка на первоисточник, пометка «модельное изменение»;
- повторное нажатие даёт тот же результат, без дублей.

Шаги проверки появятся в сценарии проверки (K-33b) и в этом разделе после слияния K-29.

## Интеграции и деградация

| Интеграция | Для чего | Без неё |
| --- | --- | --- |
| MAX Bot API | приём событий, отправка уведомлений | локальный контур и тесты работают без событий; отправка использует модельного отправителя |
| Реестр МСП ФНС | профиль по ИНН | «источник недоступен» и ручной ввод; в тестах — фикстуры |
| regulation.gov.ru | лента проектов НПА — ранние сигналы | уведомления о версиях пакетов правил продолжают работать |
| GigaChat | классификация документов ленты | `LLM_PROVIDER=template` даёт детерминированный результат без ключей; провайдер ждёт живой проверки с ключом (K-19b) |
| Локальная модель | автономный runtime ИИ | профиль Compose по умолчанию не запускается |
| PostgreSQL | хранение | в тестах — PGlite |

ИИ — только GigaChat или локальная модель ([ADR-0001](docs/decisions/0001-llm-provider-policy.md)). Текст внешних документов — недоверенные данные и не меняет инструкции модели.

Локальная модель не входит в образы приложения и запускается отдельным профилем; веса хранятся в томе `local-model-data`:

```bash
docker compose --profile local-model up --build
```

## API и внешний контур

`miniapp-api` — внутренний API собственного мини-приложения, а не публичный API ([ADR-0004](docs/decisions/0004-defaults-without-organizer-answers.md)). Перечень внутренних методов и тестовые данные появятся в этом README вместе с API; сейчас точка входа пустая.

На VPS Nginx завершает TLS на портах `80/443` и проксирует мини-приложение и webhook бота; SSH — порт `22`; база и внутренние сервисы наружу не публикуются. Развёртывание и мониторинг — [docs/deploy.md](docs/deploy.md), резервные копии и SLA пилота — [docs/operations/](docs/operations/sla.md).

## Безопасность и приватность

- секреты передаются только через окружение VPS или GitHub Secrets;
- сертификат НУЦ Минцифры кладётся в `certs/russian_trusted_root_ca.crt` и подключается только процессу Node.js через `NODE_EXTRA_CA_CERTS`, не в системное хранилище;
- `NODE_TLS_REJECT_UNAUTHORIZED=0` и аналоги запрещены и проверяются скриптом репозитория;
- логи не содержат токенов, ключей, ИНН, ОГРН, телефонов и идентификаторов пользователей;
- каждое содержательное утверждение о требовании сопровождается ссылкой на первоисточник, автоматический текст помечается;
- подпись `initData` мини-приложения будет проверяться на сервере (в работе, K-05b).

См. [certs/README.md](certs/README.md), [требования безопасности](docs/security.md) и [SECURITY.md](SECURITY.md).

## Известные ограничения MVP

- пользовательский сценарий бота и мини-приложения ещё собирается (см. «Статус проекта»);
- охват правил — два направления (общепит, автосервис) и один регион-дополнение; вне охвата сервис отвечает «вне покрытия»;
- точность зависит от полноты подтверждённого профиля; «недостаточно данных» предпочтительнее уверенной ошибки;
- источник профиля — неофициальный интерфейс реестра МСП; запасной ЕГРЮЛ ещё подключается;
- сервис работает на одном VPS без резервирования, резервные копии хранятся на нём же;
- состояние диалога, привязка чата к компании и настройки уведомлений хранятся в памяти процесса: после перезапуска бот просит ИНН заново, отключённые уведомления снова включены. На время оценки (30.09–14.10) деплой замораживается, см. `apps/worker/src/app/README.md`; хранение в PostgreSQL — Issue #312;
- демо-триггер предназначен только для демонстрации и всегда помечен как модельный;
- юридическая, нагрузочная и длительная эксплуатационная проверка — за пределами хакатонного MVP.

## Остановка и очистка

Остановить сервисы и сохранить данные:

```bash
docker compose down
```

Удалить сервисы вместе с томами PostgreSQL и весами локальной модели (необратимо):

```bash
docker compose down -v
```
