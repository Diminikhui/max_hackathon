# «Пульс» — персональные требования и возможности бизнеса в MAX

«Пульс» помогает предпринимателю не пропускать применимые к нему изменения. Сервис строит профиль компании по ИНН, сопоставляет его с правилами и мерами поддержки и присылает в MAX короткие уведомления со ссылкой на официальный первоисточник.

Продукт не заменяет юриста или бухгалтера, не рекомендует действия и не выдаёт модельные данные за официальные.

## Статус проекта

MVP для хакатона MAX (кейс «Эффективный бизнес») собран. Сдаваемая версия — коммит, на который указывает git-тег `online-submission` (`git rev-parse "online-submission^{commit}"`); после дедлайна тег не переносится. Основной сценарий подтверждён сквозным тестом K-30c, а боевой прогон K-30d пройден в web- и mobile-клиентах MAX на развёрнутом SHA `7fbaef7`. После него вошли исправления по итогам прогона (#349, #371, #373) и мини-приложение с API (#357, #364).

Уже в `main`:

- доменная модель, контракты v1 (`contracts/`) и хранилище PostgreSQL с миграциями;
- вычисление применимости: условия, пять статусов, цепочка объяснения (`packages/rules`);
- сервисы перечня, профиля и пересчёта (`packages/services`), уточняющие вопросы и объяснение дельты применимости;
- источники профиля из реестра МСП и ЕГРЮЛ/ЕГРИП, а также модельный источник (`packages/adapters`);
- пакеты правил: общепит (федеральный, налоги, отчётность и маркировка, дополнение «Татарстан», возможности) и автосервис;
- фоновые задачи: планировщик уведомлений, политика частоты, очередь и отправка в MAX (`apps/worker`); загрузка ленты regulation.gov.ru написана, но в сдаваемую сборку процесса не подключена;
- пользовательский сценарий бота: онбординг по ИНН, перечень и карточки требований, уточнения, настройки уведомлений и модельный демо-триггер (`apps/bot`);
- единый процесс `apps/worker`: webhook MAX, диалог, пересчёт, очередь и отправка уведомлений; состояние диалога, привязка чата и настройки хранятся в PostgreSQL;
- мини-приложение на MAX UI и MAX Bridge (профиль и перечень одним экраном) и его внутренний API с проверкой подписи `initData` (`apps/miniapp-api`);
- развёртывание на VPS с HTTPS, мониторингом, резервными копиями и SLA пилота.

Основной пользовательский сценарий запускается точкой входа `apps/worker/src/main.ts`; отдельный `apps/bot/src/main.ts` остаётся библиотечной заглушкой, поэтому сервис `bot` в `compose.yaml` ничего не принимает. Мини-приложение работает через собственный внутренний API (`apps/miniapp-api`), но проверяемый сценарий полностью проходит в боте. План и статусы следующих потоков — в [дорожной карте](docs/roadmap.md).

## Сценарий MVP

1. Пользователь открывает бота и вводит ИНН.
2. Сервис находит компанию в реестре МСП и предлагает подтвердить профиль: регион, ОКВЭД, категорию и численность.
3. Движок применимости относит каждое требование пакета к одному из пяти статусов: применяется / не применяется / недостаточно данных / требуется проверка / вне покрытия.
4. При «недостаточно данных» бот задаёт только те уточняющие вопросы, которые меняют результат.
5. При изменении правил пользователь получает уведомление: что изменилось, почему это касается его компании, ссылка на первоисточник и пометка об автоматической обработке.
6. Для проверки изменение показывается видимой кнопкой «🧪 Показать пример изменения (модельное)».

Основной сценарий, включая демо-изменение, проходится в боте. Мини-приложение показывает профиль и перечень одним экраном и не является обязательным для проверки.

## Как проверить решение

Основной сценарий проверяется в выданном боте MAX, а не в Docker: токен бота хранится только на сервере, а локальный контур не принимает события MAX (см. «Локально события MAX не принимаются»).

- Бот: <https://max.ru/t214_hakaton_max_bot>. Мини-приложение открывается из бота кнопкой «Open» у поля ввода.
- Тестовые ИНН — модельные компании K-28, помечены в сообщениях: `7700000016` (кофейня, Москва, все данные есть) и `1600000011` (кафе, Казань, без данных о работниках). Логины и пароли не нужны: вход по ИНН.
- Шаги (около двух минут): «Начать» → ИНН `1600000011` → «✅ Всё верно» → «📋 Мой перечень» → «❔ Уточнить данные» и ответы кнопками (первый вопрос — про налоговый режим, затем про работников) → карточка любой записи → «🔄 Другая компания» → ИНН `7700000016` → «🧪 Показать пример изменения (модельное)» → приходит уведомление «Изменение».
- Ожидаемые тексты и проверки по шагам: [docs/verification.md](docs/verification.md).
- Если бот не отвечает: повторите через минуту (реестр МСП иногда отвечает медленно) и сверьтесь с разделом «Известные ограничения MVP».

Собственный публичный API не заявляется: `miniapp-api` внутренний, описание методов — [contracts/miniapp-api.yaml](contracts/miniapp-api.yaml).

## Требования

- Git;
- Docker с Compose v2 — рекомендуемый способ запуска;
- либо Node.js 24 (`.nvmrc`, `engines` в `package.json`) и pnpm 11.19.0 (`packageManager`, включается `corepack enable`);
- PostgreSQL 17 — поднимается Compose; зависимости приложений зафиксированы в `pnpm-lock.yaml`.

## Быстрый локальный запуск

Из чистого клона:

```bash
git clone https://github.com/Diminikhui/max_hackathon.git
cd max_hackathon
cp .env.example .env
docker compose up --build --wait
```

Пустые значения в `.env` заменяются локальными значениями по умолчанию из `compose.yaml`. После запуска:

| Сервис | Адрес по умолчанию |
| --- | --- |
| Мини-приложение | <http://localhost:4173> |
| API мини-приложения | <http://localhost:3000> |
| PostgreSQL | только внутри сети Compose, порт `5432` |
| worker (webhook бота) | `127.0.0.1:3002` → `3001` в контейнере, только для nginx на сервере |
| bot | внешних портов нет; сервис-заглушка, события принимает worker |

Порты на хосте меняются через `MINIAPP_PORT`, `MINIAPP_API_PORT` и `BOT_WEBHOOK_HOST_PORT`.

Вне MAX мини-приложение не получает подписанные `initData`, поэтому экран перечня не откроется, а внутренний API отвечает `401`: это ожидаемое поведение, а не поломка. Признак успешного запуска — `docker compose ps` со статусом `healthy` у `database`, `worker`, `miniapp-api`, `miniapp`; логи — `docker compose logs -f worker`.

### Локально события MAX не принимаются

Compose запускает бота с пустым `MAX_BOT_TOKEN` и `MAX_EVENTS_ENABLED=false`, поэтому локальный контур не получает события выданного бота и не конфликтует с сервером. Токен хранится только на VPS ([ADR-0003](docs/decisions/0003-issued-bot-and-hackathon-contour.md)).

### Запуск без Docker

```bash
corepack enable
pnpm install --frozen-lockfile
pnpm build
pnpm test
```

Проверки перед Pull Request:


## Источник профиля предприятия

Порядок источников ([ADR-0006](docs/decisions/0006-adopted-gap-proposals.md), п. 7):

1. **Реестр МСП ФНС** — основной ([`MspProfileSource`](packages/adapters/src/profile/msp/README.md)). Одним запросом по ИНН даёт основной ОКВЭД, регион, категорию МСП, численность и признак лицензий. Все факты помечены как официальные, с источником и датой.
2. **ЕГРЮЛ/ЕГРИП** — запасной адаптер реализован (K-12a), но в текущую сборку процесса не подключён.
3. **Модельный источник** — фикстуры K-28 для тестов и демо, помечены `isModel`.

Ограничения реестра МСП:

- используется внутренний интерфейс страницы поиска `rmsp.nalog.ru` без спецификации: формат может измениться, тогда адаптер отвечает «источник недоступен», а не ломает сценарий. Допустимость такого интерфейса по условиям кейса — открытый вопрос организаторам;
- отклик нестабилен: адаптер по умолчанию ждёт 20 с и повторяет один раз, бот — 8 с на попытку и до трёх попыток; частый опрос не допускается;
- в реестре только субъекты МСП; исключённые из реестра компании считаются ненайденными;
- это срез: реестр обновляется 10-го числа, численность — за прошлый год или ранее;
- дополнительных ОКВЭД ответ не содержит, отсутствие работников из нуля не выводится — бот уточняет у пользователя;
- пользователь подтверждает профиль или вводит другой ИНН; поля профиля вручную править нельзя, недостающие факты бот уточняет вопросами; ИНН и название ИП не пишутся в логи.

Подробнее: [исследование реестров МСП](docs/research/k04b-msp-registers.md), [требования безопасности](docs/security.md).

## Правила и данные

Пакет правил — данные, а не код: регион и направление подключаются новым пакетом. Каждая запись содержит условие применимости, покрытие, срок и хотя бы одно основание со ссылкой на официальный акт. Статус применимости выводится воспроизводимо из правил и подтверждённых фактов: ИИ его не определяет, а только помогает классифицировать документы ленты и переформулировать готовое объяснение.

| Каталог | Содержимое |
| --- | --- |
| `data/rulepacks/a/` | общепит: федеральный пакет, налоги, отчётность и маркировка (`a-foodservice-tax-marking-fed`), дополнение «Татарстан», возможности |
| `data/rulepacks/b/` | автосервис: федеральный пакет |
| `data/rulepacks/_golden/` | эталонный перечень для оценки качества |
| `data/rulepacks/_demo-scale/` | модельная демонстрация тиражирования на новый регион и направление |
| `data/fixtures/` | модельные компании и пакеты K-28, записанные ответы источников |

Всё модельное помечено в данных, интерфейсе и сообщениях. Фикстуры K-28 описаны в [README набора](data/fixtures/k28-README.md).

## Демо-триггер

Реальное правило не успеет измениться за 10–15 минут проверки, поэтому K-29 добавляет отдельную кнопку:

- видимая кнопка бота **«🧪 Показать пример изменения (модельное)»**;
- берётся заранее подготовленная следующая версия модельного пакета, например `k28-rulepack-v2` поверх v1 с новой записью `k28.water-marking`;
- запускается тот же механизм, что при реальном изменении: новая версия пакета → планировщик → пересчёт → уведомление (контур K-30a);
- уведомление самодостаточно: что изменилось, почему касается компании, ссылка на первоисточник, пометка «модельное изменение»;
- повторное нажатие даёт тот же результат, без дублей.

Пошаговая проверка, ожидаемые тексты и модельные ИНН приведены в [сценарии проверки K-33b](docs/verification.md). Демо запускает тот же контур пересчёта и очереди уведомлений, что новая проверенная версия реального пакета, но данные и событие явно помечены как модельные.

## Дополнительные функции бота

Функции включаются переменной `BOT_FEATURES` (значения через запятую). Пустое значение — бот работает только по основному сценарию. Флаг задаёт владелец сервера; на VPS для проверки включено `examples,whatif,deadlines,explain`.

| Значение | Где в боте | Что делает | Данные |
| --- | --- | --- | --- |
| `examples` | шаг ввода ИНН: «☕ Кафе, Москва», «☕ Кафе, Татарстан», «👤 ИП без работников» | запускает онбординг для модельной компании без своего ИНН | модельные компании K-28, помечены |
| `whatif` | меню: «🔮 Что будет, если…» | сценарии «👤 Найму первого работника», «🍷 Начну продавать алкоголь», «💳 Перейду на УСН «доходы»», «📍 Буду работать в Татарстане» → какие записи появятся, исчезнут или сменят статус | сценарный расчёт на копии профиля; реальный профиль не меняется |
| `deadlines` | меню: «📅 Что и когда» | применимые обязанности по срокам: дата, «При событии», «Постоянно», «Периодически — нужна дата последнего исполнения» | даты только из текста срока и календаря 4-01; без даты — с причиной, не выдумываются |
| `explain` | карточка требования: «💬 Простым языком» | пересказ уже вычисленного результата: статус, решающие условия, источник | вход модели — только вычисленный результат. `template` — «📝 Пересказ по шаблону, без ИИ», `gigachat` — «🤖 Пересказ модели GigaChat — проверьте по источнику» |
| `cards` | кнопка «Открыть карточку» под демо-уведомлением | открывает карточку в мини-приложении | на сервере проверки выключено; включайте, только если корень сайта отдаёт мини-приложение |

### Реальные и модельные данные в боте

| Реальное | Модельное (всегда помечено) |
| --- | --- |
| профиль по ИНН субъекта МСП из реестра МСП ФНС | компании K-28 (`7700000016`, `1600000011`, `770000000082` и др.) |
| пакеты правил общепита (федеральный, налоги и маркировка, Москва, Татарстан, возможности) и автосервиса со ссылками на акты | демо-изменение пакета (`k28-rulepack-v2`) и уведомление по нему |
| вычисление применимости и ссылки на первоисточники | сценарии «Что будет, если…» |
| отправка сообщений через MAX Bot API | ответы на уточняющие вопросы — заявленные факты «по вашим словам» |

Демо-уведомление создаётся только для модельных компаний: реальному бизнесу выдуманное изменение не отправляется. Налоги, отчётность и маркировка общепита (16 записей, #329) подключены с частичным покрытием: без фактов о доходах, выплатах и товарных операциях запись получает «требуется проверка» или «недостаточно данных», а не «применяется». Записи сверены с официальными публикациями; независимая юридическая проверка не проводилась.

## Интеграции и деградация

| Интеграция | Для чего | Без неё |
| --- | --- | --- |
| MAX Bot API | приём событий, отправка уведомлений | локальный контур и тесты работают без событий; отправка использует модельного отправителя |
| Реестр МСП ФНС | профиль по ИНН | бот сообщает, что источник недоступен, и просит повторить позже; в тестах — фикстуры |
| regulation.gov.ru | лента проектов НПА — ранние сигналы; код готов, в сдаваемую сборку не подключена | уведомления о версиях пакетов правил работают без неё |
| GigaChat | пересказ «Простым языком» (2-22), классификация документов ленты | `LLM_PROVIDER=template` даёт детерминированный текст без ключей; сбой, таймаут или ответ не по схеме тоже дают шаблон. Живой вызов проверен на VPS |
| Локальная модель | автономный runtime ИИ | профиль Compose по умолчанию не запускается |
| PostgreSQL | хранение | в тестах — PGlite |

ИИ — только GigaChat или локальная модель ([ADR-0001](docs/decisions/0001-llm-provider-policy.md)). Текст внешних документов — недоверенные данные и не меняет инструкции модели.

Локальная модель не входит в образы приложения и запускается отдельным профилем; веса хранятся в томе `local-model-data`:

```bash
docker compose --profile local-model up --build
```

## API и внешний контур

`miniapp-api` — внутренний API собственного мини-приложения, а не публичный API ([ADR-0004](docs/decisions/0004-defaults-without-organizer-answers.md)). Методы (OpenAPI 3.1, [contracts/miniapp-api.yaml](contracts/miniapp-api.yaml)), базовый путь `/api`: `GET /health`, `POST` и `DELETE /v1/session` (вход по подписанному `initData` MAX), `GET /v1/profile`, `GET /v1/checklist`, `GET` и `PUT /v1/settings`. Все методы, кроме `/health`, требуют сессию; отдельных логинов нет, тестовые данные — модельные ИНН из «Как проверить решение».

На VPS Nginx завершает TLS на портах `80/443` и проксирует мини-приложение и webhook бота; SSH — порт `22`; база и внутренние сервисы наружу не публикуются. Развёртывание и мониторинг — [docs/deploy.md](docs/deploy.md), резервные копии и SLA пилота — [docs/operations/](docs/operations/sla.md).

## Безопасность и приватность

- секреты передаются только через окружение VPS или GitHub Secrets;
- сертификат НУЦ Минцифры кладётся в `certs/russian_trusted_root_ca.crt` и подключается только процессу Node.js через `NODE_EXTRA_CA_CERTS`, не в системное хранилище;
- `NODE_TLS_REJECT_UNAUTHORIZED=0` и аналоги запрещены и проверяются скриптом репозитория;
- логи не содержат токенов, ключей, ИНН, ОГРН, телефонов и идентификаторов пользователей;
- каждое содержательное утверждение о требовании сопровождается ссылкой на первоисточник, автоматический текст помечается;
- пакет `packages/security` проверяет подпись `initData` и ограничивает срок данных, а `apps/miniapp-api` выдаёт сессию только после этой проверки; правила минимизации ПДн — в [документе безопасности](docs/security.md).

См. [certs/README.md](certs/README.md), [требования безопасности](docs/security.md) и [SECURITY.md](SECURITY.md).

## Известные ограничения MVP

- основной сценарий готов и проверен в боте; мини-приложение показывает профиль и перечень и открывается только из MAX (нужна подпись `initData`); сессии API хранятся в памяти процесса и сбрасываются при перезапуске;
- охват правил — общепит в Москве и Татарстане (налоги, отчётность и маркировка — с частичным покрытием, без независимой юридической проверки), возможности для общепита и тонкий пакет автосервиса; вне охвата сервис отвечает «вне покрытия»;
- точность зависит от полноты подтверждённого профиля; «недостаточно данных» предпочтительнее уверенной ошибки;
- источник профиля — неофициальный интерфейс реестра МСП; адаптер ЕГРЮЛ/ЕГРИП и загрузка ленты regulation.gov.ru готовы, но в сборку процесса не подключены;
- реального ручного ввода профиля нет: если ИНН не найден в реестре МСП (например, компания не субъект МСП), сценарий дальше не идёт;
- сервис работает на одном VPS без резервирования, резервные копии хранятся на нём же;
- состояние диалога, привязка чата к компании и настройки уведомлений хранятся в PostgreSQL, но сервис по-прежнему работает одним процессом на одном VPS; на время оценки (30.09–14.10) деплой замораживается, см. `apps/worker/src/app/README.md`;
- K-30d подтвердил основной путь на SHA `7fbaef7`; в ручной проверке одно сообщение пришло три раза из-за трёх быстрых нажатий кнопки без подтверждения. Это не сбой доставки: очередь отправки дублей не давала (дедупликация по ключу проверена сквозными тестами). Исправлено в PR #349, повторная проверка в MAX нужна на новой версии;
- демо-триггер предназначен только для демонстрации и всегда помечен как модельный;
- юридическая, нагрузочная и длительная эксплуатационная проверка — за пределами хакатонного MVP.

## Остановка и очистка

Остановить сервисы и сохранить данные:

```bash
docker compose down
```

Повторный запуск после остановки (данные сохраняются в томе `postgres-data`):

```bash
docker compose up -d --wait
```

После изменения кода добавляйте `--build`.

Удалить сервисы вместе с томами PostgreSQL и весами локальной модели (необратимо):

```bash
docker compose down -v
```
