# Политика частоты уведомлений (K-20b)

Чистая детерминированная функция, которая решает, что делать с `NotificationCandidate` от планировщика (K-20a). Базу данных, часы и настройки функция не читает: вызывающий код передаёт их в контексте.

```ts
import { decide, decideAll, countInMskMonth } from "./planner/policy/index.js";

decide(candidate, { isDuplicate, sentThisMonth, settings, relevance }, config?)
// → { action: "send" | "digest" | "suppress", code, countsTowardLimit }
```

## Правила

Правила проверяются по порядку, срабатывает первое подходящее.

| # | Условие | Действие | Код |
|---|---|---|---|
| 1 | кандидат с тем же `dedupKey` у компании уже есть (`NotificationRepository.hasCandidate`) или встречался раньше в этом прогоне | `suppress` | `duplicate` |
| 2 | компания отключила уведомления (`settings.enabled = false`) | `suppress` | `notifications_disabled` |
| 3 | `early_signal`, а ранние сигналы отключены (`settings.earlySignals = false`) | `suppress` | `early_signals_disabled` |
| 4 | `early_signal` без оценки релевантности | `suppress` | `relevance_unknown` |
| 5 | `early_signal` с релевантностью ниже порога (по умолчанию 0,5) | `suppress` | `below_relevance_threshold` |
| 6 | причина важная: `became_applicable`, `no_longer_applicable` | `send` (даже сверх лимита) | `priority_reason` |
| 7 | в текущем месяце по МСК компании отправлено уже `monthlyLimit` уведомлений | `digest` | `monthly_limit_reached` |
| 8 | иначе | `send` | `within_monthly_limit` |

- **Лимит по умолчанию — 4 уведомления в календарный месяц МСК** (`DEFAULT_MONTHLY_LIMIT`), настраивается через `monthlyLimit`. Концепт обещает «единицы сообщений в месяц». Замер ленты regulation.gov.ru показал 1,8–2,8 значимых документа в месяц на отрасль ([предложения](../../../../../docs/proposals/2026-09-23-gaps-and-proposals.md)). Значение 4 покрывает обычный месяц с запасом и отсекает всплески.
- **Важные изменения не теряются молча.** Новая или снятая обязанность отправляется сверх лимита, но расходует его, поэтому остальное в этом месяце уходит в сводку. Изменение статуса (`status_changed`) и ранний сигнал сверх лимита получают `digest`: вызывающий код откладывает их в ежемесячную сводку и не удаляет.
- **Отключение побеждает всё**, включая новые обязанности: пользователь сам отказался от уведомлений. Перечень обязанностей (бот, мини-приложение) при этом остаётся доступен.
- **Порог релевантности** действует только на `early_signal`. Изменения по правилам детерминированы и не оцениваются.
- **Модельные кандидаты** (`isModel: true`) проходят те же правила.
- **Месяц** — календарный по Москве (UTC+3, без перехода на летнее время): `mskMonthKey`. Лимит расходуют уведомления со статусом `sent` (месяц по `sentAt`) и `queued` (по `createdAt`), см. `countInMskMonth`. `failed` и `suppressed` лимит не расходуют.
- Коды причин (`POLICY_DECISION_CODES`) стабильны. Их пишут в журнал и метрики, поэтому коды не переименовывают, а только добавляют новые.

## Как использовать

- **K-30a (контур уведомлений):** для прогона вызовите `decideAll(candidates, ctx)`, где `ctx.isDuplicate` — результат `hasCandidate` (заранее прочитанный), `ctx.sentThisMonth` — счётчик компании. Внутри прогона функция сама учитывает дубли и расход лимита. Затем:
  - `send` — `saveCandidate`, затем `enqueue` уведомления;
  - `digest` — `saveCandidate` и пометка для ежемесячной сводки;
  - `suppress` — код причины записывается в журнал. Если код не `duplicate`, вызовите `saveCandidate`, чтобы повтор распознавался как дубль.
- **K-24c / 2-05 (настройки):** храните `NotificationSettings { enabled, earlySignals }` и передавайте их в контекст. Лимит компании при необходимости задаётся через `config.monthlyLimit`.
