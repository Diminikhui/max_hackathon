# Сборка процесса «Пульса» (K-30b)

Один процесс — контейнер `worker` — держит всё, что нужно для сценария проверки в MAX:

```text
MAX ──webhook──► createBotHttpServer (POST /webhook, GET /health)
                   └─ createInboundDispatcher → createBotApp (apps/bot/src/app)
                        ├─ онбординг K-24a, перечень K-24b, настройки K-24c, уточнения K-09
                        ├─ демо-кнопка K-29 → NotificationPipeline K-30a → очередь уведомлений
                        └─ ответы в чат: POST /answers (замена нажатого сообщения) или POST /messages
runSendLoop → SendQueueWorker → MaxMessageSender K-21b ──► MAX (push из очереди)
```

Почему один процесс: бот и контур уведомлений читают одни настройки уведомлений и один справочник получателей push, а `apps/worker` зависит от `apps/bot`, поэтому бот не может импортировать контур уведомлений (решение — комментарий в Issue #143).

| Файл | Что делает |
| --- | --- |
| `runtime.ts` | `assembleApp` — сборка без сети (её проходят тесты на PGlite); `startApp` — запуск: PostgreSQL, webhook, цикл отправки |
| `config.ts` | переменные окружения; секреты не выводятся |
| `rulepacks.ts` | пакеты, которые загружаются при старте, и граница: модельные пакеты видят только модельные компании |
| `profiles.ts` | модельные ИНН K-28 — из фикстуры, остальные — из реестра МСП (попытка 8 с, 2 повтора); итог каждого поиска в реестре — событие журнала `profile.lookup` со статусом, кодом ошибки и длительностью, без ИНН (#370) |
| `demo.ts` | демо-прогон контура: журнал событий без «потребления» перехода и только модельные компании |
| `max-reply.ts` | ответы диалога через общий rate-limited транспорт MAX |

## Что происходит при старте

1. Миграции PostgreSQL.
2. Загрузка пакетов правил, если их версии ещё нет в хранилище: общепит (федеральный, Татарстан, возможности), автосервис и модельный `k28-model` v1. Повторный старт ничего не меняет и не откатывает v2, опубликованную демо-кнопкой.
3. Если `MAX_EVENTS_ENABLED` не `true` — процесс на этом останавливается и ничего не отправляет (локальный контур, ADR-0003).
4. Иначе — HTTP-сервер бота на `BOT_HTTP_PORT` (3001 внутри контейнера) и цикл отправки очереди.

## Переключение VPS с эхо-обработчика K-05a на бота (для K-30d)

Сейчас nginx проксирует `/webhook` на `127.0.0.1:3001`, где работает `max-hackathon-webhook.service` (эхо). Контейнер `worker` публикует свой порт на `127.0.0.1:${BOT_WEBHOOK_HOST_PORT:-3002}`, поэтому два процесса не конфликтуют, пока переключение не сделано.

1. В `/etc/max-hackathon/compose.env` добавить `MAX_EVENTS_ENABLED=true`, `MAX_BOT_TOKEN=…` и `MAX_WEBHOOK_SECRET=…` (тот же secret, что в `webhook.env` и в подписке MAX).
2. Дождаться выкладки или запустить `systemctl start max-hackathon-deploy.service`; проверить `curl -fsS http://127.0.0.1:3002/health`.
3. Переключить nginx: `location = /webhook { proxy_pass http://127.0.0.1:3002; }`, затем `nginx -t && systemctl reload nginx`.
4. Остановить эхо: `systemctl disable --now max-hackathon-webhook.service`. События MAX должен получать только один процесс.
5. Проверить в MAX: «Начать» → ИНН `7700000016` → «✅ Всё верно» → меню с кнопкой «🧪 Показать пример изменения (модельное)».

Подписку MAX менять не нужно: URL и secret остаются прежними.

## Правило чата: кнопки только у последнего сообщения бота

Каждый ответ бота уходит **новым сообщением внизу чата** (`POST /messages`), а у предыдущего сообщения бота кнопки снимаются: `PUT /messages?message_id=…` с пустым `attachments` и прежним текстом (текст остаётся, его можно перечитать). Нажатие подтверждается `POST /answers` с пустым телом. Поэтому нажать кнопку из старого сообщения нельзя, а меню не копятся. Push-уведомления из очереди в это правило не входят: они остаются со своими кнопками. Сбой снятия кнопок или подтверждения пишется в лог и диалог не прерывает. Реализация: `apps/bot/src/app/handler.ts` (`deliver`) и `max-reply.ts`.

Не проверено вживую: формат тела `PUT` и пустого `POST /answers` подтверждается на боевом прогоне K-30d.

## Ограничения

- **Всё состояние хранится в PostgreSQL** (#312): диалог, привязки, настройки уведомлений, чат компании для push и пропущенные вопросы уточнения, а также профили, пакеты, кандидаты и очередь уведомлений. Перезапуск контейнера диалог не сбрасывает. В памяти остаются только дедупликация событий webhook и последнее сообщение бота с кнопками: после перезапуска у этого сообщения кнопки не снимаются, а нажатие на них работает как обычно.
- Фоновый цикл уведомлений по реальным пакетам (`runNotificationLoop`) и лента regulation.gov.ru в этой сборке не запускаются: до сдачи новые версии реальных пакетов не публикуются, а изменение показывается демо-кнопкой.
- Ранние сигналы в настройках сохраняются, но сейчас не отправляются (флаг `earlySignals` контура выключен).

## Заморозка деплоя на время оценки

После тега `online-submission` (3-11b) сервер не обновляется: изменения идут в ветки и PR, но в `main`, откуда деплой берёт код, не сливаются до объявления результатов (это же сказано в чеклисте сдачи `docs/submission.md`, PR #300). Состояние диалога перезапуск уже не сбрасывает (#312), но на время перезапуска бот недоступен, а новый код может изменить сценарий посреди проверки. Если исправление всё же необходимо, слияние согласуется с владельцем сервера, а проверяющих не должно быть посреди сценария. Для остановки обновлений: `sudo systemctl stop max-hackathon-deploy.timer`, для возобновления: `sudo systemctl start max-hackathon-deploy.timer`.

## Где хранится состояние бота (#312)

Миграция `packages/storage/migrations/k-30b-001-bot-dialogs.sql`, репозитории — `packages/storage/src/bot/`. Сборка передаёт их в `createBotApp` и контур уведомлений в `assembleApp`.

| Что | Таблица | Репозиторий → порт бота |
| --- | --- | --- |
| состояние диалога | `bot_dialogs.state` | `PostgresBotDialogRepository` → `DialogStateStore`; неизвестное значение читается как `idle` |
| профиль до подтверждения, привязка «диалог → компания» | `bot_dialogs.pending_profile`, `company_id` | `PostgresBotDialogRepository` → `OnboardingSessions`; смена компании (#310) перезаписывает привязку |
| пропущенные вопросы уточнения | `bot_dialogs.clarify_skipped` | `PostgresClarifySkipRepository` → `ClarifySkipStore` |
| чат компании для push | `bot_chat_companies` | `PostgresChatDirectoryRepository` → `ChatDirectory` и `RecipientDirectory` K-30a: чат — последний, где компания выбрана |
| настройки уведомлений | `notification_settings` | `PostgresNotificationSettingsRepository` → `NotificationSettingsStore`; тот же экземпляр читает `NotificationPipeline` |

Реализации в памяти (`DialogChatDirectory`, `createMemoryDialogStateStore`, `createMemorySettingsStore`, `InMemoryOnboardingSessions`, `createMemorySkipStore`) остаются для тестов бота. Проверка перезапуска — `apps/worker/test/app/runtime.test.ts`: `assembleApp` повторно на той же базе PGlite.
