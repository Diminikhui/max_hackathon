# K-28. Модельные данные ядра и сценарий проверки

> **Все данные в `k28-*` — модельные.** Компании, ИНН и записи пакета вымышлены. ИНН проходят проверку контрольной суммы, но реальным организациям не принадлежат. Записи пакета иллюстрируют механизм и **не являются юридическими утверждениями**. В интерфейсе, README и презентации такие данные помечаются модельными.

## Пошаговый сценарий проверки

1. **Перечень.** Кофейня `7700000016` → 6 записей: 4 «применяется», «требуется проверка» (санитария, формализована частично), «вне покрытия» (спецлицензия). У каждой записи — объяснение и ссылка на источник.
2. **Уточняющие вопросы.** Кафе `1600000011` → «недостаточно данных» по двум записям; система спрашивает «Есть работники?» и «Продаёте алкоголь?» (`missingFactKeys`). После ответов «да» и «пиво» (заявленные факты) обе записи — «применяется».
3. **Не применяется.** Автосервис `7700000023` → записи общепита «не применяется» с причиной «ОКВЭД начинается с 56 — не выполнено».
4. **Ошибка данных.** Кафе `7700000030` → обязанность работодателя «требуется проверка», а не «применяется» или «не применяется».
5. **Демо-изменение.** Публикация `k28-rulepack-v2` поверх v1: разница — добавлена `k28.water-marking`; уведомление получают `k28-cafe-msk` и `k28-cafe-bad-data` (ОКВЭД 56 и Москва), остальные — нет.

Для проверки в боте (K-30b, K-33b) профили загружаются в хранилище вместо ответа реестра МСП (fixture-реализация `ProfileSource`, K-11), пакет — через `saveVersion` (K-10b).
