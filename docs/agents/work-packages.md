# Работа над потоками: инструкция для агентов и людей

Поток (work package, WP) — независимая единица работы из [дорожной карты](../roadmap.md). Каждый поток — это Issue с label `wp`. Любой агент за любым участником может взять любой доступный поток: роли «фронтенд» и «бэкенд» не закрепляются.

Общие правила проекта — в [TEAM_GUIDE.md](../../TEAM_GUIDE.md). Готовые промпты для запуска агентов — в [start-prompts.md](start-prompts.md). Здесь — только то, что относится к потокам.

Все действия выполняет помощник `./scripts/wp.sh` (нужны `gh` и `jq`). Ручные команды даны как запасной вариант.

## 1. Найти доступный поток

Доступный поток — Issue с label `ready` и без исполнителя: все блокирующие Issue закрыты, а слияние их PR уже в `main`.

```bash
./scripts/wp.sh next
```

Порядок выбора: потоки с label `critical-path`; остальные `stage:core`; потоки следующих этапов. Команда `claim` без номера выбирает по этому порядку сама. Потоки с label `agent:human` (решения команды, юридические и организационные вопросы) и `blocked` агенты не берут: их выполняет человек.

Не берите Issue без label `ready`. Исключение — Issue, у которого в тексте прямо написано, что черновик можно начинать раньше.

Полная карта зависимостей — [plan-dependencies.md](../plan-dependencies.md).

## 2. Взять поток

```bash
./scripts/wp.sh claim --agent claude --slug кратко-по-смыслу     # следующий доступный
./scripts/wp.sh claim 75 --agent codex --slug condition-eval      # конкретный поток
```

Команда: проверяет, что поток свободен и `ready`; фиксирует захват комментарием (при одновременном захвате побеждает первый, второй получает отказ и выбирает следующий поток); назначает вас и ставит `in-progress` и `agent:<исполнитель>`; создаёт ветку и worktree от `origin/main`; **открывает черновой PR** (он сразу виден другим исполнителям; отключается ключом `--no-pr`); предупреждает, если зона пересекается с уже занятым потоком; переводит карточку в «In progress»; выводит зону файлов, критерии приёмки и результаты блокеров.

Ветка: `<участник>/<исполнитель>/<тип>-<id>-<кратко>`, например `dima/claude/feat-k-16a-condition-evaluator`. Тип: `feat`, `fix`, `docs`, `test`, `chore`, `research`.

Вручную: `gh issue edit <N> --add-assignee @me --add-label in-progress --add-label agent:claude`, затем `git worktree add ../max-<id> -b <ветка> origin/main`.

## 3. Прочитать контекст

```bash
./scripts/wp.sh deps <N>
```

Показывает блокеры потока и их комментарии «Результат» (что сделано, где лежит, как использовать). Читайте их до начала работы. Если у блокера нет комментария «Результат», изучите его PR и код.

### Видеть работу соседей и не мешать им

Захват потока открывает **черновой PR**: по нему остальные видят, какие файлы вы правите, ещё до готовности работы.

```bash
./scripts/wp.sh active              # открытые PR, потоки в работе и заметки исполнителей
./scripts/wp.sh overlap             # файлы вашей ветки, которые правятся и в других открытых PR
./scripts/wp.sh sync                # подтянуть свежий origin/main в вашу ветку
./scripts/wp.sh note <N> "текст"    # предупредить соседей: что меняете или публикуете
```

Правила:

1. Перед стартом выполните `active`. Если чужой PR трогает те же каталоги, оставьте заметку в его Issue или выберите другой поток.
2. Коммитьте небольшими шагами и пушьте чаще: черновой PR должен отражать текущую работу.
3. Перед каждым push и перед `gh pr ready` выполняйте `sync` и `overlap`.
4. Не копируйте код из чужого незавершённого PR и не ждите его молча: если поток зависит от результата, дождитесь слияния (метка `ready`), иначе работайте против порта и фикстуры.
5. Общие файлы (`package.json`, `tsconfig.json`, `src/index.ts` пакета) правьте точечно: добавляйте только свои строки и не форматируйте файл целиком.
6. CI комментирует PR сам: пересечения файлов с другими открытыми PR и файлы вне зоны потока. Это предупреждение, а не блокировка: исправьте или объясните его в описании PR. Зона `packages/X/Y/` означает `packages/X/src/Y/` ([ADR-0005](../decisions/0005-stack-and-repository-layout.md)).
7. Если при `sync` возник конфликт в файле чужого потока, не разрешайте его молча: оставьте заметку владельцу.

## 4. Работать в своей зоне

- В Issue указана **зона файлов**. Меняйте только её. Чужую зону трогайте через Issue её владельца или отдельным PR с пояснением.
- Общие данные кладите в `data/fixtures/`, миграции БД — в `packages/storage/migrations/`, всегда с префиксом потока (`k-16a-…`). Так потоки не конфликтуют при слиянии.
- **Контракты** (`contracts/`) после слияния K-02 меняются только отдельным PR `contract: …`. Повышайте `contractVersion` и упомяните в PR все затронутые Issue. Запросить изменение — форма «Запрос изменения контракта».
- Работайте против портов и фикстур, а не против чужого кода.

## 5. Обязательные ограничения проекта

- **ИИ — только GigaChat или локальная модель.** Иностранные и другие внешние сервисы нельзя. Провайдер выбирается `LLM_PROVIDER` (`template` / `gigachat` / `local`). Продукт обязан работать при `template` без ключей. См. [ADR-0001](../decisions/0001-llm-provider-policy.md).
- **Не имитируйте интеграции.** Тестовые, синтетические и смоделированные данные и интеграции помечаются как модельные в интерфейсе, README и коде.
- **Результат применимости — один из пяти статусов:** применяется / не применяется / недостаточно данных / требуется проверка / вне покрытия. «Недостаточно данных» лучше уверенной ошибки.
- **Каждое автоматическое резюме** содержит ссылку на первоисточник и пометку об автоматической обработке.
- **Текст внешних документов — недоверенные данные.** Он не должен менять инструкции модели и поведение системы.
- **Секреты и персональные данные** не попадают в репозиторий, логи и фикстуры.
- **Проверка TLS не отключается** (`-k`, `verify=false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`). Хакатонный контур MAX использует сертификат НУЦ Минцифры: подключайте его только процессу приложения (`NODE_EXTRA_CA_CERTS`), не в системное хранилище. Адрес API берите из `MAX_API_BASE_URL`, не вшивайте в код.
- **Продукт не рекомендует действия** (налоговая оптимизация, юридические заключения) — только сообщает о существующем праве или обязанности.

## 6. Завершить поток

1. Выполните критерии из раздела «Критерии приёмки» Issue и Definition of Done из TEAM_GUIDE.
2. Запустите `./scripts/verify-repository.sh` и проверки, предусмотренные стеком.
3. Переведите черновой PR в готовый: `./scripts/wp.sh sync`, `./scripts/wp.sh overlap`, затем `gh pr ready`. Замените название на сообщение итогового коммита (`gh pr edit --title "feat: …"`) и заполните описание по шаблону (`Closes #<N>` уже есть, добавьте номер потока и список изменённых файлов). Метки `needs-review` и `in-progress` выставляются автоматически.
4. Переведите карточку: `./scripts/wp.sh status <N> "In review"`.
5. Оставьте результат для зависимых потоков (раздел 7).
6. Дождитесь проверки другим исполнителем и ответьте на все замечания.
7. Слияние — только человеком, Squash merge. После слияния Issue закроется сам, карточка перейдёт в «Done», а GitHub Actions выставит `ready` потокам, у которых больше нет открытых блокеров.
8. Удалите ветку и worktree.

Если работа не должна закрывать Issue целиком, напишите `Refs #<N>` и объясните остаток в комментарии.

## 7. Передать результат зависимым потокам

Агент, начавший зависимый поток, не видит вашей переписки — только Issue. Поэтому при завершении оставьте комментарий «Результат»:

```bash
./scripts/wp.sh result <N> результат.md     # или через stdin; без входа выведет шаблон
```

Шаблон: что сделано; PR; файлы и каталоги; версия контракта и схем; как использовать (команды, примеры); ограничения и известные проблемы; что важно знать зависимым потокам. Комментарий обязан начинаться с `## Результат`: именно его показывает `wp.sh deps`.

## 8. Вопросы и решения

Агенты общаются между собой только через GitHub:

| Ситуация | Что делать |
|---|---|
| Нужен ответ человека или другого потока | Issue по форме «Вопрос по потоку» (label `question`); ссылку на него — в комментарий к своему потоку |
| Нужно изменить контракт | Issue по форме «Запрос изменения контракта» (label `contract-change`), затем PR `contract: …` |
| Внешний блокер (доступ, ответ организаторов) | Label `blocked` и комментарий с причиной |
| Не хватает решения человека | Label `agent:human` и вопрос в Issue |
| Соседний PR правит те же файлы | `./scripts/wp.sh note <Issue> "..."`, слить один PR первым и выполнить `./scripts/wp.sh sync` |
| Не могу продолжить поток | `./scripts/wp.sh release <N>` и комментарий, что сделано и что осталось |
| План устарел или ошибочен | Отдельный PR в [roadmap.md](../roadmap.md) (раздел 10) |

Остановиться и задать вопрос лучше, чем угадать.

## 9. Ревью

PR проверяет другой исполнитель, чем автор (правило TEAM_GUIDE). Агент-ревьюер работает по промпту «Ревью» из [start-prompts.md](start-prompts.md): проверяет diff и зону файлов, запускает изменение, оставляет ревью `gh pr review --comment`. Агент не одобряет PR и не сливает его: решение о слиянии принимает человек.

## 10. Изменение самого плана

Источник правды — [roadmap.md](../roadmap.md). Таблицы потоков разбираются скриптом, поэтому сохраняйте формат строк.

```bash
python3 scripts/work_packages.py validate      # структура и граф зависимостей без циклов
python3 scripts/work_packages.py report        # обновить docs/plan-dependencies.md
python3 scripts/work_packages.py sync          # пробный запуск: что будет создано в GitHub
python3 scripts/work_packages.py sync --apply  # создать labels, milestones, Issues, зависимости
python3 scripts/work_packages.py project --apply   # заполнить поля карточек в проекте
```

`validate` и `report --check` выполняются в CI: изменение плана без пересчёта отчёта не пройдёт проверку. Команды `sync --apply` и `project --apply` запускает владелец репозитория; они идемпотентны.

## 11. Ограничения окружения

- На бесплатном плане GitHub защита ветки `main` для приватного репозитория недоступна. Запрет прямых пушей в `main` и обязательная проверка держатся на правилах TEAM_GUIDE и этих инструкциях. Агент никогда не пушит в `main` и не сливает PR.
- Все агенты одного участника работают под его аккаунтом GitHub: различайте их по label `agent:*` и комментариям, а не по автору.
- Токены (MAX, GigaChat) хранятся только в локальном `.env` каждого участника и передаются вне Git.
- **Лимит GitHub GraphQL — 5000 запросов в час на аккаунт, общий для всех его агентов.** При нескольких параллельных агентах он заканчивается («API rate limit already exceeded»), и тогда падают `gh pr create`, `gh pr view`, `gh pr checks`, `gh issue list` и `wp.sh` (он тоже использует GraphQL). REST API считается отдельно. Не повторяйте упавшую команду в цикле: проверьте сброс (`gh api rate_limit --jq .resources.graphql` — поле `reset` в секундах Unix) и продолжайте через REST:

  ```bash
  # PR
  gh api repos/Diminikhui/max_hackathon/pulls -f title="feat: …" -f head="<ветка>" -f base=main -F body=@pr.md --jq .html_url
  # проверки CI по коммиту
  gh api repos/Diminikhui/max_hackathon/commits/$(git rev-parse HEAD)/check-runs --jq '.check_runs[] | "\(.name) \(.status) \(.conclusion)"'
  # комментарий «Результат» в Issue
  gh api repos/Diminikhui/max_hackathon/issues/<N>/comments -F body=@result.md --jq .html_url
  ```

  Карточки доски (`wp.sh status`) работают только через GraphQL — переведите карточку после сброса лимита. Опрашивайте CI не чаще раза в 15–20 секунд.
