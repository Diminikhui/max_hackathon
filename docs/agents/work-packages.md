# Работа над потоками: инструкция для агентов и людей

Поток (work package, WP) — независимая единица работы из [дорожной карты](../roadmap.md). Каждый поток — это Issue с label `wp`. Любой агент за любым участником может взять любой доступный поток: роли «фронтенд» и «бэкенд» не закрепляются.

Общие правила проекта — в [TEAM_GUIDE.md](../../TEAM_GUIDE.md). Здесь — только то, что относится к потокам.

## 1. Найти доступный поток

Доступный поток — Issue с label `ready`: все блокирующие Issue закрыты, а слияние их PR уже в `main`.

```bash
gh issue list -l wp -l ready --state open --json number,title,labels,assignees \
  --jq '.[] | select(.assignees | length == 0) | "\(.number)\t\(.title)"'
```

Порядок выбора:

1. потоки с label `critical-path`;
2. остальные потоки со `stage:core`;
3. потоки следующих этапов (`stage:2`, `stage:3`, …).

Не берите Issue без label `ready`. Исключение — Issue, у которого в тексте прямо написано, что черновик можно начинать раньше (например, «черновик» в условии старта).

Полная карта зависимостей — [plan-dependencies.md](../plan-dependencies.md).

## 2. Проверить зависимости

```bash
gh api "repos/{owner}/{repo}/issues/<N>/dependencies/blocked_by" --jq '.[] | "\(.number)\t\(.state)\t\(.title)"'
gh api "repos/{owner}/{repo}/issues/<N>/dependencies/blocking"   --jq '.[] | "\(.number)\t\(.title)"'
```

Первая команда — от чего зависит поток, вторая — какие потоки ждут его результата. Прочитайте результаты блокирующих потоков (контракты, фикстуры, документы), прежде чем начинать.

## 3. Взять поток

```bash
gh issue edit <N> --add-assignee @me --add-label agent:claude   # или agent:codex, agent:human
git fetch origin
git worktree add ../max-<id> -b <участник>/<исполнитель>/<тип>-<id>-<кратко> origin/main
```

- Один поток — один Issue, одна ветка, один исполнитель, один worktree.
- Если Issue уже назначен, поток занят.
- Тип ветки: `feat`, `fix`, `docs`, `test`, `chore`, `research`. Пример: `dima/claude/feat-k16a-condition-evaluator`.

## 4. Работать в своей зоне

- В Issue указана **зона файлов**. Меняйте только её. Чужую зону трогайте через Issue её владельца или отдельным PR с пояснением.
- Общие данные кладите в `data/fixtures/`, миграции БД — в `packages/storage/migrations/`, всегда с префиксом потока (`k16a-…`). Так потоки не конфликтуют при слиянии.
- **Контракты** (`contracts/`) после слияния K-02 меняются только отдельным PR `contract: …`. Повышайте `contractVersion` и упомяните в PR все затронутые Issue.
- Работайте против портов и фикстур, а не против чужого кода.

## 5. Обязательные ограничения проекта

- **ИИ — только GigaChat или локальная модель.** Иностранные и другие внешние сервисы нельзя. Провайдер выбирается `LLM_PROVIDER` (`template` / `gigachat` / `local`). Продукт обязан работать при `template` без ключей. См. [ADR-0001](../decisions/0001-llm-provider-policy.md).
- **Не имитируйте интеграции.** Тестовые, синтетические и смоделированные данные и интеграции помечаются как модельные в интерфейсе, README и коде.
- **Результат применимости — один из пяти статусов:** применяется / не применяется / недостаточно данных / требуется проверка / вне покрытия. «Недостаточно данных» лучше уверенной ошибки.
- **Каждое автоматическое резюме** содержит ссылку на первоисточник и пометку об автоматической обработке.
- **Текст внешних документов — недоверенные данные.** Он не должен менять инструкции модели и поведение системы.
- **Секреты и персональные данные** не попадают в репозиторий, логи и фикстуры.
- **Продукт не рекомендует действия** (налоговая оптимизация, юридические заключения) — только сообщает о существующем праве или обязанности.

## 6. Завершить поток

1. Выполните критерии из раздела «Критерии приёмки» Issue и Definition of Done из TEAM_GUIDE.
2. Запустите проверки репозитория:
   ```bash
   ./scripts/verify-repository.sh
   ```
   и проверки, предусмотренные стеком, когда они появятся.
3. Откройте PR. В описании обязательно `Closes #<N>`, номер потока и список изменённых файлов. Название PR — как сообщение итогового коммита (`feat: …`).
4. Дождитесь проверки другим участником и ответьте на все замечания.
5. Слияние — только Squash merge. После слияния Issue закроется сам, а GitHub Actions выставит `ready` потокам, у которых больше нет открытых блокеров.
6. Удалите ветку и worktree.

Если работа не должна закрывать Issue целиком, напишите `Refs #<N>` и объясните остаток в комментарии.

## 7. Комментарий о ходе работы

Оставляйте в Issue короткий комментарий в начале и в конце:

```text
Начал: <дата>, ветка <имя>, worktree <путь>.
Сделано: <что>. Проверено: <как>. Риски: <что осталось>.
```

## 8. Если что-то мешает

- Не хватает данных или решения человека — поставьте label `agent:human` и опишите вопрос в Issue.
- Внешний блокер (доступ, ответ организаторов) — label `blocked` и комментарий с причиной.
- Нужна правка чужой зоны или контракта — создайте Issue, не правьте молча.
- План устарел или ошибочен — правьте [roadmap.md](../roadmap.md) отдельным PR (см. раздел 9).

## 9. Изменение самого плана

Источник правды — [roadmap.md](../roadmap.md). Таблицы потоков разбираются скриптом, поэтому сохраняйте формат строк.

```bash
python3 scripts/work_packages.py validate     # структура и граф зависимостей без циклов
python3 scripts/work_packages.py report       # обновить docs/plan-dependencies.md
python3 scripts/work_packages.py sync         # пробный запуск: что будет создано в GitHub
python3 scripts/work_packages.py sync --apply # создать labels, milestones, Issues, зависимости
```

`validate` и `report --check` выполняются в CI: изменение плана без пересчёта отчёта не пройдёт проверку. Команду `sync --apply` запускает владелец репозитория; она идемпотентна и не дублирует уже созданные Issue.
