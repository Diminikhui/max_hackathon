## Как читать документ

Каждый пункт устроен одинаково:

1. **В репозитории / Новое** — что уже есть у команды и что предлагается сверх этого.
2. **Что сейчас** — как обстоит дело по документам и фактам, со ссылкой на источник.
3. **Проблема** — почему это мешает сдаче, баллам или продукту.
4. **Варианты** — возможные решения с плюсами и минусами (если решение не очевидно).
5. **Рекомендация** — какой вариант предлагается и почему.

Метки у утверждений:

- **[факт]** — проверено; рядом указано, как именно.
- **[гипотеза]** — правдоподобно, но не проверено; указано, как проверить.
- **[решение]** — нужен выбор команды; без него работа по пункту не начинается.

### Что в системе автоматическое, а что ручное

Это различие — источник большинства разночтений, поэтому проговаривается отдельно.

```text
АВТОМАТИЧЕСКИ, для любой компании в России      ВРУЧНУЮ, на каждое направление и регион
────────────────────────────────────────        ─────────────────────────────────────────
ИНН → реестр МСП → профиль                       пакет правил: какие обязанности есть,
  (ОКВЭД, регион, численность)                   по какому акту, кому применяются
вычислитель: профиль × пакет → статусы           (готовой машиночитаемой базы
планировщик: новая версия пакета → уведомления    «вид деятельности → обязанность → условие» нет)
бот, мини-приложение, доставка
```

Код пишется один раз. Пакеты правил пополняются с каждым новым направлением и регионом. Новое направление или регион — это новый файл пакета, а не изменение кода.

## 2. Хостинг и доступность бота на период оценки

- **В репозитории:** задач про сервер, домен, HTTPS и работу бота на период оценки нет (проверено поиском по roadmap, концепту и архитектуре). `docs/architecture.md`: «схема развёртывания фиксируется отдельным ADR после выбора стека» — такого ADR нет. О персональных данных — только «не коммитить» и «минимизация ПДн» (K-32b); о месте хранения данных ничего нет.
- **Новое:** задача развёртывания; конфликт общего токена; вопрос о месте хранения данных.

**Требование кейса.** Бот или мини-приложение должны оставаться доступны для прохождения основного сценария весь период оценки: 30.09–14.10. «Контейнеризация не заменяет работающую версию продукта в MAX». Мини-приложение подключается к MAX только по HTTPS.

**Проблема 1.** Если бот запущен на ноутбуке участника, он недоступен, когда ноутбук выключен. Две недели оценки проверяющие заходят в произвольное время.

**Проблема 2. [гипотеза, проверить в K-05c]** Токен бота один. Проверяющий получает его с первого слайда и может запустить `docker compose up` у себя. Тогда два процесса (наш сервер и копия у проверяющего) одновременно получают события одного бота. Возможные последствия: сообщения делятся между процессами, и у каждого сценарий обрывается; либо, если на сервере настроен webhook, локальный long polling не получает событий вообще.

**Проблема 3. [гипотеза, проверить юридически]** ИНН и ФИО индивидуального предпринимателя — персональные данные. Закон о персональных данных требует хранить данные граждан РФ на серверах в России. Это влияет на выбор хостинга.

## 3. Главная ценность продукта — уведомление при изменении — не видна при проверке

- **В репозитории:** уведомление возникает при новой версии пакета (K-30a); события ленты изменений — под флагом. Задача 2-10 уже определяет deep link из уведомления на конкретное требование как кандидата на платформенный бонус. Концепт (раздел 14): «демо, где кофейня получает три точных уведомления, сильнее…». Механизма, с помощью которого уведомление появится во время проверки, нет.
- **Новое:** демо-триггер, его связка с 2-10 и правило самодостаточности уведомления.

**Что сейчас.** Концепт строит ценность на том, что бот пишет первым, когда меняется правило или бизнес («push, не каталог»). В ядре основной сценарий — перечень по ИНН.

**Проблема.** Проверка занимает 10–15 минут; за это время ни одно правило не изменится. Проверяющий увидит перечень по ИНН и оценит продукт как каталог — то, от чего концепт прямо отстраивается (разделы 4–5). Главная ценность в оценку не попадёт.

**Предложение: демо-триггер.**
- Кнопка бота «🧪 Показать пример изменения (модельное)».
- По нажатию система берёт заранее подготовленную следующую версию пакета (например, v2 с одной новой записью) и запускает тот же механизм, что и при реальном изменении: планировщик → пересчёт перечня → уведомление. **Настоящий механизм, модельный только источник изменения.**
- Уведомление содержит:
  - что изменилось;
  - почему это касается именно этой компании (какие факты профиля совпали с условием);
  - ссылку на первоисточник;
  - пометку «модельное изменение».
- Кнопка «Открыть карточку» в уведомлении открывает карточку новой обязанности в мини-приложении — это deep link из задачи 2-10. Демо-триггер делает сценарий 2-10 проверяемым, а значит, делает реальным и платформенный бонус (+0,15).
- **Уведомление самодостаточно:** всё перечисленное выше есть в самом сообщении бота, а кнопка открывает подробности. Основной сценарий, включая демо-изменение, проходится только в боте. Причина: мини-приложению нужны публичный HTTPS и проверка подписи `initData`, у него больше точек отказа. Если оно недоступно во время проверки, сценарий не обрывается и допуск не теряется. В roadmap этот принцип задан структурой этапов (ядро — бот, мини-приложение — этап 2); без явного правила демо-триггер создал бы зависимость основного сценария от мини-приложения.
- Повторное нажатие должно давать тот же результат, то есть триггер сбрасывается для пользователя. Причина: критерий «стабильность при повторном прохождении».
- Шаг описывается в сценарии проверки (K-33b), README и на первом слайде, иначе проверяющий о нём не узнает.

**Как это видит проверяющий.**

1. Ввести ИНН тестовой кофейни → перечень из 20 обязанностей.
2. Нажать «🧪 Показать пример изменения».
3. Получить уведомление:

```text
🔔 Новое требование (модельное изменение)
С 1 марта: передавать данные о продаже упакованной воды
в систему маркировки.

Почему это вас касается: ОКВЭД 56.10 · Москва · продажа напитков
Источник: постановление № … (ссылка)
[Открыть карточку]
```

4. Нажать «Открыть карточку» → мини-приложение открывается на этой обязанности: основание, срок, что сделать.

**Варианты размещения триггера.**

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Видимая кнопка с пометкой «модельное» | Проверяющий точно найдёт | Кнопка видна и обычным пользователям (для хакатона допустимо) |
| Б. Скрытая команда, описанная в README и на слайде | Не засоряет интерфейс | Проверяющий может не прочитать |
| В. Автоматическое модельное изменение через минуту после онбординга | Ничего нажимать не нужно | Неожиданно для пользователя; сложнее повторить |

**Рекомендация: А.**

## 4. Гипотеза Г2: поле есть, но это не ОКВЭД

- **В репозитории:** Г2 записана как непроверенная гипотеза (концепт, раздел 9.2); проверка — задача K-18c. Риск «нет ОКВЭД» в таблице рисков концепта: «запасной вариант — ручная разметка узкого набора ОКВЭД для демо». Задача K-18a ориентирована на метод API `/api/npalist/`.
- **Новое:** результат проверки, найденные методы API и вывод для отбора ленты изменений.

**Что такое Г2.** Концепт предполагает, что в карточке каждого проекта акта на regulation.gov.ru указаны коды ОКВЭД тех, кого акт затрагивает. Причина: при процедуре оценки регулирующего воздействия (ОРВ) ведомство обязано указать затрагиваемых. Если это так, ленту изменений можно автоматически сопоставлять с ОКВЭД компании без LLM (раздел 9.3 концепта).

**Что проверено. [факт, 22–23.09.2026, запросы без авторизации]**
- `GET /api/npalist/` (метод из K-18a) — поля ОКВЭД нет.
- `GET /api/public/PublicProjects/GetProjectStageInfo/{id}/0` (паспорт проекта) содержит поле «Виды экономической деятельности».
- `POST /api/public/PublicProjects/GetFiltered` фильтрует проекты по этому полю на сервере (`filters: "okveds==23"`) и по тексту заголовка (`title@=текст`).
- **Значения поля — не коды ОКВЭД.** Справочник `GET /api/public/Okveds` содержит 60 укрупнённых сфер со своими идентификаторами:
  - 23 — «Гостиницы и рестораны»;
  - 45 — «Ремонт автотранспортных средств»;
  - 22 — «Оптовая и розничная торговля».
- ⚠️ **Идентификатор сферы не совпадает с кодом ОКВЭД:** id «56» означает «Регистрация права собственности и постановка на кадастровый учёт», а не общепит.
- Поле заполнено у всех 178 свежих проектов, обычно одна сфера; 39% помечены «Государственное управление».
- **Разметка неполная:** «Правила оказания услуг общественного питания» (проект 165513) отнесены к «Государственному управлению», требования к автосервисам (165887) — к «Транспорту».
- За 12 месяцев: сфера 23 — 9 проектов, сфера 45 — 6, сфера 22 — 42 (много лишнего).

**Проблема.** Отбор ленты «по ключу ОКВЭД», как в разделе 9.3 концепта, невозможен:
- **Слишком крупно.** «Гостиницы и рестораны» — одна сфера; кофейню от гостиницы по ней не отличить.
- **Пропуски.** Только по сфере важнейший для общепита проект года был бы пропущен. Концепт сам называет пропуск при отборе недопустимой ошибкой («человек не получил важное уведомление, тихо»).
- **Полезная часть:** сфера — официальный серверный фильтр. Не нужно скачивать все проекты (~725 в месяц) и разбирать их самим.

**Варианты отбора ленты.**

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| А. Комбинация сигналов | Сфера ИЛИ ключевые слова в заголовке ИЛИ ведомство (Роспотребнадзор и т.п.); результат показывается как «обсуждается проект, который может вас касаться», статус «требуется проверка» | Детерминированно, воспроизводимо, честно | Есть пропуски и лишние срабатывания |
| Б. Классификация через LLM (GigaChat) | Модель решает, касается ли проект отрасли | Точнее ключевых слов на сложных текстах | Недетерминированно; противоречит ADR-0001 («модель не определяет применимость») |
| В. Лента не показывается; только версии пакета | Изменения попадают к пользователю после того, как человек обновил пакет | Точно и объяснимо | Задержка; нужен человек |

**Рекомендация: А + В.** Лента — ранний сигнал со статусом «требуется проверка»; точная персональная дельта — через версии пакета.

В результате пользователь получает сообщения двух разных типов:

| | Ранний сигнал (лента) | Точное уведомление (пакет) |
|---|---|---|
| Что это | Проект акта, ещё не действует | Принятое требование |
| Откуда | Автоматический фильтр по regulation.gov.ru, раз в сутки; отбор делает код, без LLM | Человек разобрал принятый акт и выпустил новую версию пакета (п. 16) |
| Формулировка | «Обсуждается проект, который может вас касаться» | «Касается вас, потому что ОКВЭД 56.10 + Москва + есть работники» |
| Статус | «требуется проверка» | «применяется» и т.д. |
| Что нужно от пользователя | Ничего; это ранний сигнал | Выполнить к сроку |

Статус «требуется проверка» означает, что система честно сообщает: точно определить применимость она не может. Он **не** означает «разбирайтесь сами». Пример раннего сигнала:

```text
📋 Обсуждается проект (может вас касаться)
Роспотребнадзор: изменения в санитарные правила для общепита.
Статус: проект, обсуждение до 15 октября. Ещё не действует.
Касается ли вас — требуется проверка: проект отобран по сфере
«Гостиницы и рестораны», точные условия ещё не разобраны.
Источник: regulation.gov.ru/projects/… (ссылка)
```

LLM (GigaChat) в ленте допустима только для пересказа заголовка простым языком. При `LLM_PROVIDER=template` показывается исходный заголовок.

**Следствие для питча.** Нельзя утверждать «мы автоматически сопоставляем законы с вашим ОКВЭД». Корректная формулировка: проекты отбираются заранее по нескольким официальным признакам и помечаются как требующие проверки; точный перечень обязанностей ведётся вручную с источниками.

**Попутная находка. [факт]** На regulation.gov.ru есть процедура «Принятие решения о порядке предоставления субсидий» — официальный поток новых мер поддержки.

## 6. База правил — ручная работа; объём растёт с каждым направлением и регионом

- **В репозитории:** принцип «регион, направление и правила — подключаемые данные, а не код» (roadmap, принцип 7). Три направления × два региона (ADR-0002). Пакет K-17a — «федеральные + Москва + Татарстан» в одном пакете. Поле «владелец» в формате пакета (K-15b). Демонстрация нового региона и направления (3-02). ФГИС РОТ как real-источник (K-13b) с оговоркой о доступе. Проверочные листы упомянуты только как атрибут требования в ФГИС РОТ.
- **Новое:** сокращение объёма; разделение на федеральный пакет и региональные дополнения; проверочные листы как основа чеклиста.

**Почему это ручная работа.**
1. Данные о компании и алгоритм универсальны (см. раздел 0). **Правила — нет.** В актах не написано «ОКВЭД 56». Там написано «организации общественного питания», «работодатели», «лица, осуществляющие продажу пива». Перевести это в условие («ОКВЭД начинается с 56 И есть работники») может только человек, прочитавший акт. Проверка Г2 (п. 4) подтвердила, что готовой разметки по ОКВЭД у источников нет.
2. **Одного ОКВЭД недостаточно даже внутри направления.** Маркировка зависит от продаваемых товаров, ЕГАИС — от продажи алкоголя, СОУТ — от наличия работников.
3. **Регионы различаются правилами, а не данными.** Их устанавливают сами регионы, и автоматического источника «все региональные требования к кафе в Казани» нет. Примеры:
   - торговый сбор есть только в Москве (московский закон);
   - часы продажи алкоголя ограничивает каждый регион;
   - региональные субсидии и гранты;
   - московские правила размещения вывесок и летних веранд.

**Предлагаемая структура пакетов** (вместо одного пакета «федеральные + Москва + Татарстан»):

```text
федеральный пакет направления «общепит»   ← пишется один раз, действует во всех регионах
  + региональное дополнение «Москва»       ← только московские отличия
  + региональное дополнение «Татарстан»    ← только татарстанские отличия
```

Разделение нужно для пункта 9: федеральная часть применяется к компаниям из любого региона.

**Проблема.** 3 направления × 2 региона — это 3 федеральных пакета и 6 региональных дополнений ручной работы за неделю, из них одна задача (K-06a → K-17a) на критическом пути.

**Варианты объёма. [решение]**

| Вариант | Состав | Плюсы | Минусы |
|---|---|---|---|
| А. Как в ADR-0002 | 3 направления глубоко × 2 региона | Широкий охват | Объём не помещается в срок |
| Б. Одно глубоко + одно тонко | Общепит — полный федеральный пакет + Москва полностью. Автосервис — 5–7 записей. Татарстан — 3–5 региональных отличий. Розница — после сдачи | Помещается в срок; вживую показывает «новое направление = новый файл» и «новый регион = новый файл», а это демонстрация масштабирования | Меньше охват |
| В. Минимум | Только общепит, только Москва | Минимальный объём | Масштабирование только заявлено, а не показано; 35% продуктовой оценки под риском |

**Рекомендация: Б.** Масштабирование — 35% продуктовой оценки. Критерий требует показать условия адаптации, а не перечислить регионы. Второй регион и второе направление в тонком виде — самый дешёвый способ показать это делом.

**Источник для пакета общепита. [гипотеза]** Брать за основу официальные проверочные листы контрольных органов:
- Роспотребнадзор — санитария;
- МЧС — пожарная безопасность;
- Роструд — трудовое право.

Это готовый перечень того, что проверит инспектор, с основаниями, и готовый ответ на вопрос жюри «откуда список». Совпадает с направлением кейса «Контроль и надзор… проверочные листы». Ограничения:
- в листах только то, что проверяется на проверках; налоги, отчётность, маркировку нужно добавлять из других источников;
- наличие и актуальность листов для общепита нужно проверить первым шагом задачи K-06a.

**Кто пишет пакеты при масштабировании** (вопрос жюри будет). В MVP — вручную. В промышленной версии — из ФГИС РОТ с проверкой человеком.

**Проверка ФГИС РОТ. [факт, 23.09.2026]**
- Геоблокировки нет. Прежняя ошибка доступа вызвана сертификатом: сайт подписан удостоверяющим центром Минцифры, которому стандартные хранилища не доверяют. Это тот же вопрос, что с MAX (ADR-0003): доверять корню Минцифры, а не отключать проверку TLS. Для разведки проверка временно отключалась (`curl -k`); в коде это запрещено.
- **Машинный доступ есть.** `POST https://ot.gov.ru/api/mandatoryRequirement/list`, тело `{"items":[],"paging":{"page":1,"count":100}}`, возвращает JSON без авторизации. Всего **542 536** требований.
- **Требования структурированы:**
  - `activitySubtype` — коды ОКВЭД (например, `49.39.12`, `46.11`; часто `00` — «все виды деятельности»);
  - `categoriesOfPersons` — категории обязанных лиц;
  - `controlTypes` — ссылки на проверочные листы и перечни подтверждающих документов;
  - `interestedFOIV` — ведомство;
  - `checkQuestion` — контрольный вопрос инспектора.
- **Не работает:**
  - фильтр по ОКВЭД на сервере (`activitySubtype=56.10`): через 120 секунд — ошибка шлюза; текстовый фильтр сервер игнорирует;
  - официальный набор открытых данных Минцифры «Обязательные требования» (`7710474375-mrlist`): схема отдаётся, заявленный адрес `/api/opendata/mrlist` возвращает 404;
  - полная выгрузка тяжёлая: около 100 записей за 5 секунд, около 13 КБ на требование; весь реестр — порядка 7 ГБ и нескольких часов. Для ночной синхронизации возможно, для хакатона нет.
- **Не проверено:** насколько полно размечен ОКВЭД для 56, 45.2, 47. В небольшой неслучайной выборке большая часть записей помечена `00`. Если это так по всему реестру, фильтр по ОКВЭД выдаст кофейне тысячи общих требований — та же картина, что с Г2 (п. 4).

**Вывод.** Узкое место — не доступ, а **отбор и проверка**. Формулировка для питча: «В MVP пакеты для выбранных видов деятельности собраны вручную. При масштабировании источник — ФГИС „Реестр обязательных требований“: более 540 тыс. требований, уже разложенных по ОКВЭД, категориям лиц и видам контроля; машинный доступ проверен. Готового фильтра по ОКВЭД нет, и у многих требований стоит „все виды деятельности“, поэтому пакет по новому ОКВЭД собирает машина из реестра, а человек проверяет перед публикацией (п. 16). Уведомление уходит только из проверенной версии пакета». Подробности про объём и таймауты — ответ на вопрос «почему не полностью автоматически», вслух не нужны.

Дополнительно: поле `controlTypes` связывает требования с проверочными листами. Это подтверждает, что проверочные листы — рабочая основа для пакета общепита.

## 7. Масштабирование: усилия направлены на количество, а не на перенос

- **В репозитории:** этап 3 включает и перенос (3-01 — загрузчик пакетов, 3-02 — новый регион и направление без правок кода, 3-07 — материалы масштабирования), и количественный масштаб (3-03 — генератор 5 млн компаний, 3-04a/b — хранилище и пересчёт под 5 млн, 3-06 — нагрузочные замеры).
- **Новое:** предложение отложить количественную часть с опорой на формулировку кейса.

**Требование кейса.** Масштабирование — 35% продуктовой оценки. Кейс прямо пишет: думать о масштабировании «не как о количестве потенциальных пользователей, а как о возможности перенести решение в другой контекст». Критерий: конкретные регионы и контексты, условия адаптации (данные, интеграции, ресурсы), ограничения и риски, реалистичный порядок тиражирования.

**Проблема.** Четыре задачи (3-03, 3-04a, 3-04b, 3-06) работают на количественный масштаб, который кейс не оценивает.

**Рекомендация.**
- Отложить 3-03, 3-04a, 3-04b, 3-06 до после сдачи.
- Сосредоточиться на трёх задачах:
  - 3-01 — загрузчик пакетов;
  - 3-02 — новый регион или направление без изменения кода, показать вживую;
  - 3-07 — документ «что остаётся неизменным, что адаптируется, порядок тиражирования, риски».
- Производительность обосновать словами: отбор — индексный запрос, время почти не растёт с числом компаний.

## 8. Персональные изменения редки: риск «молчащего бота»

- **В репозитории:** концепт — «из тысячи документов в месяц кофейне уходит два», метрика «среднее число уведомлений в месяц — единицы». Лимит частоты уведомлений (K-20b). Регулярные сроки — «очередь действий»: vision и этап 4 (4-01, 4-02). Измерений частоты и механики против долгой тишины нет.
- **Новое:** измеренная частота; риск долгой тишины; ежемесячная сводка для MVP.

**Что измерено. [факт, оценка]** Выгрузка 7000 последних проектов regulation.gov.ru, полные месяцы январь–август 2026:
- около 725 проектов в месяц;
- из них с процедурой ОРВ — около 102 в месяц; с высоким или средним регулирующим воздействием — около 53;
- по ключевым словам в заголовках, ОРВ высокого или среднего воздействия: общепит около 1,8 в месяц, автосервис около 2,8, розница около 1,9;
- по сфере regulation.gov.ru (п. 4): «Гостиницы и рестораны» — 9 проектов за 12 месяцев.

**Ограничения оценки:**
- фильтр по словам грубый: есть и лишние, и пропущенные;
- учтены только федеральные проекты; региональных актов на портале нет;
- проект ≠ изменение: часть проектов не принимается, от проекта до вступления в силу проходят месяцы.

Изменения со стороны бизнеса ещё реже: реестр МСП обновляется раз в месяц (10-го числа), численность — раз в год, ОКВЭД меняют редко.

**Выводы.**
1. Оценка концепта «кофейне единицы сообщений в месяц, а не десятки» подтверждается по порядку величины. Это готовый ответ на вопрос жюри «как часто вы будете писать».
2. Изменений, которые **точно** применимы к конкретной компании, будет несколько в год. Бот, который молчит месяцами, перестают воспринимать, и первое уведомление могут не открыть.

**Варианты. [решение]**

| Вариант | Суть | Объём | Когда |
|---|---|---|---|
| А. Ежемесячная сводка | «За месяц проверено N документов, вас касается K» | Шаблон сообщения + подсчёт | MVP |
| Б. Три момента на одно изменение | Проект опубликован → принят → вступает в силу | Нужна связь проекта с принятым актом | После сдачи |
| В. Регулярные сроки | Напоминания о сроках, не пересекающихся с работой бухгалтера: замена фискального накопителя кассы, продление медкнижек, повтор СОУТ, продление лицензий | «Очередь действий» из этапа 4 | Пилот, финал |
| Г. Ничего не делать | — | — | Риск остаётся |

**Рекомендация.** А — в MVP. В — назвать в презентации как следующий шаг пилота.

## 9. Компании вне Москвы и Татарстана получают пустой результат

- **В репозитории:** регионы MVP — Москва и Татарстан; статус «вне покрытия» определён для правил и сфер. Поведение для компании из другого региона не описано.

**Что сейчас.** Реестр МСП отдаёт профиль по любому региону. Большая часть обязанностей общепита — федеральные.

**Проблема.** Компания из другого региона, скорее всего, получит «вне покрытия» целиком, хотя федеральная часть к ней применима. Проверяющие часто вводят произвольный реальный ИНН (свой, знакомой компании).

**Варианты.**

| Вариант | Что видит кафе из Самары | Оценка |

## 10. Статус «недостаточно данных» — тупик для пользователя

- **В репозитории:** статус «недостаточно данных» (концепт 8.8, roadmap). Заявленные факты хранятся отдельно от официальных и не затирают их (K-25b). Правка профиля в мини-приложении (2-02). Механизма, который при статусе «недостаточно данных» запрашивает у пользователя недостающий факт, нет.
- **Новое:** уточняющие вопросы как шаг основного сценария.

**Когда он возникает.** Реестр знает о компании немного: ОКВЭД, регион, размер, численность. Многие обязанности зависят от того, чего в реестре нет:

| Запись правила | Нужный факт | Есть в реестре? |
|---|---|---|
| ЕГАИС, лицензия на алкоголь | Продаёт ли компания алкоголь; какой (пиво или крепкий) | Нет: ОКВЭД 56.10 этого не показывает |
| Маркировка упакованной воды, молочной продукции, соков | Продаёт ли такие товары | Нет |
| Договор с РАО/ВОИС | Звучит ли музыка в зале | Нет |
| Согласование летней веранды (Москва) | Есть ли веранда | Нет |
| СОУТ, медкнижки | Есть ли работники | Обычно да (`od2_sschr`); у новых компаний поле бывает пустым |

**Проблема.** Критерий UX требует «в основном сценарии нет тупиков». Если бот показывает «недостаточно данных» и ничего не предлагает, пользователю нечего сделать.

**Варианты.**

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| А. Уточняющие вопросы после профиля | Бот задаёт только вопросы, ответ на которые меняет результат (3–5 вопросов): «Продаёте алкоголь?» [Да, пиво] [Да, крепкий] [Нет] | Модель 5 статусов становится видимым полезным шагом; вопросов мало | Нужна логика «какие вопросы влияют на результат» |
| Б. Анкета при онбординге | Все вопросы сразу, до перечня | Проще реализовать | Длинный вход; часть вопросов не нужна |
| В. Оставить статус с пояснением | «Недостаточно данных: неизвестно, продаёте ли вы алкоголь» | Минимум работы | Остаётся тупиком |

**Рекомендация: А.** Уточнение, чтобы не было разночтений:
- **Система не решает субъективно, относится ли правило к пользователю.** Решает условие записи, всегда одинаково.
- Ответ пользователя только **заполняет недостающий факт**. Он сохраняется как заявленный (по правилу K-25b) и помечается в карточке: «по вашим словам: продаёте пиво».
- После ответа перечень пересчитывается.

## 12. Проблема не подтверждена данными и интервью

- **В репозитории:** задачи 3-12 («обоснование актуальности… интервью с предпринимателями») и 2-13 («UX-сценарий: As-Is / To-Be») — не начаты. Концепт позиционирует продукт против платных сервисов «для бухгалтера».
- **Новое:** гипотеза о текущем способе, позиционирование относительно бухгалтера, вопросы интервью, данные — содержание для задач 3-12 и 2-13.

**Требование кейса.** Критерий «пользовательская ценность» (25% продуктовой оценки) — востребованность подтверждена данными, наблюдениями или аргументированными допущениями. В финале — снова 25%.

**Что сейчас.** Г1 (сколько времени занимает ручной сбор обязанностей) и интервью с предпринимателями не выполнены или не отражены в репозитории.

**Гипотеза о текущем способе (As-Is). [гипотеза, проверить интервью]** Формулировка сегмента «без штатного бухгалтера» не означает «без бухгалтера вообще». Вероятно, у большинства микробизнесов есть бухгалтер на аутсорсе. Одного человека, знающего все обязанности, нет; их закрывают несколько исполнителей по частям:

| Исполнитель | Что закрывает | Что не закрывает |
|---|---|---|
| Бухгалтер на аутсорсе | Учёт, налоги, отчётность, зарплата | Санитария, пожарная безопасность, маркировка на практике, алкогольная лицензия |
| Поставщик кассы и учётной системы | ККТ, ЕГАИС, маркировка (продаёт под них решения) | Остальное |
| Консультанты по санитарии | Производственный контроль, ХАССП | Остальное |
| Пожарная компания | Пожарная безопасность | Остальное |
| Отраслевые чаты, коллеги | Отдельные случаи | Системность, достоверность |
| Инспектор, штраф | — | Узнаёт владелец, когда уже поздно |

Целостную картину собирает сам владелец. Об изменениях он узнаёт, если их заметил исполнитель соответствующей части.

**Позиционирование, которое из этого следует.** Продукт **не заменяет бухгалтера**: граница концепта — не считаем налоги и не советуем. Он закрывает то, что выпадает между исполнителями: единая карта обязанностей всех частей плюс сигнал, когда в какой-то части что-то изменилось. Для питча: «Бухгалтер знает ваши налоги. Мы показываем всё остальное и не даём пропустить изменения».

**Предложение.**
- Г1 выполнить при составлении пакета общепита: засечь, сколько времени занял сбор.
- 3–5 интервью с владельцами кафе по 15 минут. Вопросы:
  1. Кто следит за налогами, санитарией, пожарной безопасностью, маркировкой?
  2. Как вы узнали о последнем новом требовании: от кого и когда?
  3. Были ли штрафы или предписания, о которых вы не знали заранее?
  4. Сколько стоит это сопровождение в месяц?
- Данные для обоснования:
  - число субъектов МСП с ОКВЭД 56 в Москве и Татарстане (реестр МСП);
  - статистика из кейса: 63 тыс. дистанционных контрольных мероприятий через приложение «Инспектор» за январь–апрель 2026 против 17,7 тыс. за весь 2025 год. Контроль становится частым и дистанционным.
- Для пилота: бухгалтеры на аутсорсе как канал привлечения (один бухгалтер ведёт 20–50 микрокомпаний).

## 16. Процесс обновления пакетов не описан; предложение — «ИИ готовит, человек подтверждает» (HITL)

- **В репозитории:** инструменты для обновления есть. У пакета есть версия, владелец, источник, срок действия (K-15b, концепт 8.8). Валидатор отклоняет некорректный пакет (K-15c). Команда `pack add` подключает пакет без правки кода (3-01). Новая версия пакета запускает уведомления (K-30a). Проверка вторым участником — только для первичного сбора (K-06a). Концепт 8.8: неоднозначные и высокорисковые случаи решаются с участием человека. ADR-0001: модель может извлекать структуру из документов, но не определяет применимость.
- **Новое:** описание процесса (источник принятых актов, роль, регулярность, проверка, публикация) и схема HITL.

**Что сейчас.** Не описано:
1. **Откуда человек узнаёт, что акт принят.** Лента смотрит только проекты на regulation.gov.ru. Принятые акты публикуются на `publication.pravo.gov.ru`. Концепт называет этот портал источником (раздел 9.1), но задачи на него нет. Связь «проект из ленты → принятый акт» не описана.
2. **Кто обновляет пакет и как часто.** Нет роли (например, «редактор пакета общепита») и регулярности.
3. **Кто проверяет правку.** Проверка вторым человеком предусмотрена только для первичного сбора.
4. **Как правка попадает к пользователям.** Предположительно: PR с изменением пакета → слияние → новая версия на сервере → планировщик. Нигде не записано.

**Проблема.**
- Для сдачи 29.09 это почти не критично: демо-триггер (п. 3) показывает механизм и без описанного процесса.
- Для защиты критично. Жюри спросит: «кто поддерживает правила и что произойдёт, когда закон изменится?». Это же входит в критерии масштабирования («данные, интеграции, ресурсы, участники процесса») и пилота («владельцы процесса»).
- Ручное составление пакетов — главное узкое место масштабирования (п. 6). Без ответа, как его сократить, история масштабирования неполная.

**Предлагаемый процесс.**

```text
1. Ранний сигнал (автоматически, раз в сутки)
   regulation.gov.ru → фильтр (п. 4) → «обсуждается проект, может вас касаться»

2. Принятый акт (редактор, регулярно — например, раз в неделю)
   publication.pravo.gov.ru + проекты из ленты, по которым вышел итоговый акт

3. Черновик записи (ИИ, по желанию)
   GigaChat читает текст акта и предлагает черновик записи пакета:
   «Новая обязанность: … Кому: ОКВЭД 56 + есть работники. С 01.03.2027. Основание: п. 4.2»
   При LLM_PROVIDER=template черновик — заголовок + ссылка; условие заполняет редактор

4. Решение (человек)
   редактор видит черновик рядом с текстом акта:
   [✅ Подтвердить]  [✏️ Исправить]  [❌ Не касается]
   второй человек проверяет подтверждённую запись по первоисточнику

5. Публикация (автоматически)
   новая версия пакета → валидатор → планировщик → точные уведомления
```

Разделение ответственности, чтобы не было разночтений:
- **ИИ** только предлагает черновик (извлечение структуры, допустимое по ADR-0001). Он не решает, касается ли акт кого-либо.
- **Человек** утверждает запись и ставит ссылку на первоисточник. Юридическое решение — за ним.
- **После подтверждения** правило применяется детерминированным вычислителем, как любое другое.
- Ответ на вопрос жюри «кто отвечает за ошибку»: каждая запись подтверждена человеком по первоисточнику, ссылка есть в карточке.

**Кто редактор при масштабировании.** В MVP — участник команды. В пилоте — сотрудник оператора, например регионального центра «Мой бизнес». При масштабировании черновики для нового направления формируются из ФГИС РОТ: машинный доступ проверен, отбор и проверку выполняет человек по этому же процессу (п. 6).
