# Дорожная карта: ядро и этапы

Документ согласует [концепт](../koncept-hackathon-max.md) с условиями кейса «Эффективный бизнес». Каждый этап — законченный продукт, который можно сдать без следующих. Дата составления: 19.09.2026; дедлайн онлайн-тура — 30.09.2026; точное время неизвестно, поэтому ориентир — готовность к 29.09.2026 23:59 МСК ([ADR-0004](decisions/0004-defaults-without-organizer-answers.md)).

## 1. Рамка

- **Видение:** единый проактивный слой между государством и бизнесом в MAX для всего российского бизнеса.
- **Название продукта:** «Пульс» ([ADR-0002](decisions/0002-team-decisions.md)).
- **Приоритетный сегмент MVP:** микробизнес и ИП с работниками без штатного бухгалтера и юриста; до сдачи 29.09 общепит (56) — полностью, автосервис (45.2) — тонким пакетом; розничная торговля (47) — после сдачи; регионы — Москва полностью, Республика Татарстан — тонким дополнением ([ADR-0006](decisions/0006-adopted-gap-proposals.md)). Остальные отрасли и регионы — предмет масштабирования, а не MVP.
- **Основной сценарий:** ИНН → профиль → персональный перечень обязанностей с источником и датой → уведомление об изменении.
- **Граница продукта:** сообщаем о праве или обязанности, не рекомендуем действие. Автоматическая обработка помечена, рядом ссылка на первоисточник.
- **Собственный публичный API не заявляем:** баллов он не даёт, а требует OpenAPI, тестовых учёток и `DATA-API.yaml`. Внутренние методы мини-приложения описываем в OpenAPI с первого дня, чтобы при необходимости быстро заявить API (см. раздел 10).

### Принципы архитектуры

1. Каждый внешний источник — адаптер с единым контрактом и тремя реализациями: `real`, `fixture`, `synthetic`.
2. Отбор «кому и что применимо» детерминирован. Искусственный интеллект только извлекает структуру и переформулирует; система полностью работает и без него.
3. **Допустимый ИИ — только GigaChat или локальная модель.** Внешние иностранные сервисы не используются. Провайдер выбирается настройкой `LLM_PROVIDER`: `template` (по умолчанию, без ИИ) / `gigachat` / `local`. Проверяющий запускает продукт без ключей и получает рабочий результат.
4. Результат применимости: `применяется` / `не применяется` / `недостаточно данных` / `требуется проверка` / `вне покрытия`.
5. Тип факта виден всегда: официальный / заявленный / вычисленный / сценарный / модельный.
6. Тестовые и смоделированные данные явно помечены в интерфейсе, README и презентации.
7. Регион, ОКВЭД-направление и правила — подключаемые данные, а не код.
8. Компоненты общаются через порты и контракты (`contracts/`). Пока зависимость не готова, поток работает против порта и фикстуры.
9. Текст документов из внешних источников — недоверенные данные: он не может менять инструкции модели и поведение системы.
10. Проверка TLS-сертификатов не отключается (`-k`, `verify=false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`). Сертификаты НУЦ Минцифры подключаются только процессу приложения и в системное хранилище компьютеров не устанавливаются.
11. Основной сценарий, включая демо-изменение, проходится только в боте. Мини-приложение его дополняет: ему нужны публичный HTTPS и проверка `initData`, и его сбой не обрывает сценарий.
12. Правила направления — федеральный пакет плюс региональные дополнения. Федеральная часть применяется к компании из любого региона.
13. Лента regulation.gov.ru — ранний сигнал со статусом «требуется проверка». Точное персональное уведомление уходит только из подтверждённой человеком версии пакета.

## 2. Как работать потоками

Поток (WP, work package) — независимая единица работы. Любой агент за любым участником может взять любой доступный поток. Роль «фронтенд / бэкенд» не закрепляется.

1. **Доступный поток** — тот, у которого все зависимости из колонки «Старт после» уже смержены в `main`. Порядок выбора: ⚑ критический путь → остальное `[ЯДРО]` → потоки следующих этапов.
2. **Один поток = один Issue = одна ветка = один исполнитель = один worktree.** Ветка: `<участник>/<исполнитель>/<тип>-<id>-<кратко>`, например `dima/claude/feat-k-16a-condition-evaluator`. Правила — в [TEAM_GUIDE.md](../TEAM_GUIDE.md).
3. **Зона файлов.** Поток меняет только свою зону (колонка «Зона»). Чужую зону — только через Issue её владельца или отдельный PR с пояснением.
4. **Обозначения.** ID с буквой (`K-16a`) — конкретная часть потока. ID без буквы (`K-16`) в колонке «Старт после» означает все части. `K-17*` — любое из направлений.
5. **Контракты не дробятся.** K-02 делает один исполнитель, ревьюят двое: разрез контракта между людьми даёт расхождения. После слияния K-02 каталог `contracts/` меняется только отдельным PR `contract: …` с пометкой в Issue затронутых потоков и повышением `contractVersion`.
6. **Фикстуры и миграции.** Общие данные лежат в `data/fixtures/`, миграции БД — в `packages/storage/migrations/`; каждый поток добавляет файлы только со своим префиксом `<id>-`, поэтому конфликтов слияния нет.
7. **Готовность потока** = «Готово, когда» из таблицы + Definition of Done из TEAM_GUIDE.
8. **Размер:** **S** — до полудня, **M** — около дня, **L** — два дня и более. Потоки размера L дробятся дальше, если есть независимые части.

## 4. Этап 1. ЯДРО `[ЯДРО]`

Самодостаточный продукт: бот в MAX, который по ИНН собирает профиль, показывает персональный перечень обязанностей на выбранных направлениях и сообщает об изменениях. Запускается одной командой Docker. Работает на реальных данных там, где доступ есть, и на явно помеченных фикстурах там, где нет.

**Сдаётся:** полный работающий продукт в узком срезе (ориентир — 24.09).

**Вход:** ничего. **Параллельно с ядром** можно вести потоки раннего старта (раздел 9).

### Порядок работы: сначала сквозной сценарий

Ядро собирается сначала насквозь, затем углубляется ([ADR-0006](decisions/0006-adopted-gap-proposals.md)). Сквозной сценарий — ИНН → профиль → перечень на модельном пакете → демо-изменение → уведомление в боте — собирается из K-05a, K-22a, K-22b, K-21b, K-26, K-24a, K-24b, K-30a, K-30b и K-29. Для этого K-26 стартует на модельном пакете из K-28, а K-30a не ждёт ленту изменений. Пакеты направлений, уточняющие вопросы, покрытие и лента подключаются к уже работающему сценарию по мере готовности. Эталон K-06a и пакет K-17a не объединяются: к моменту решения K-06a уже на ревью.

## 11. Трекинг в GitHub

План живёт в этом файле, а работа — в GitHub. Соответствие задаёт скрипт [`scripts/work_packages.py`](../scripts/work_packages.py).

| Что | Как устроено |
|---|---|
| Поток | Issue с названием `[ID] …` и label `wp`; в тексте — результат, критерии приёмки, зона файлов, ссылки на блокирующие Issue |
| Зависимости | Нативные связи GitHub «blocked by / blocking» между Issue |
| Группировка | Эпики на каждую волну ядра и каждый этап; потоки подключены как sub-issues |
| Сроки | Milestones: ядро — 24.09, этап 2 — 27.09, этап 3 — 30.09, этап 4 — 29.10 |
| Доступность | Label `ready` ставится, когда закрыты все блокеры; GitHub Actions ([work-package-status.yml](../.github/workflows/work-package-status.yml)) снимает и выставляет его сам |
| Метки | `wp`, `epic`, `ready`, `in-progress`, `needs-review`, `critical-path`, `contract-change`, `question`, `stage:*`, `size:S/M/L`, `area:*`, `research`, `agent:*` |
| Работа агентов | Помощник `scripts/wp.sh` (взять поток, блокеры и результаты, статус, результат, освободить), метки PR (`pr-status.yml`), формы вопроса и запроса изменения контракта; промпты — [start-prompts.md](agents/start-prompts.md) |
| Доска | GitHub Project «MAX Hackathon — MVP»: канбан по статусу, виды «Доступно сейчас», «Критический путь», «Ядро», «Прогресс этапов» (эпики с полосой Sub-issues progress), дорожная карта; поля Этап, Слой, Поток, Критический путь, Size, Priority, Area, Agent |
| Даты Roadmap | Start date и Target date — скользящее условное расписание: считается от сегодняшнего дня при неограниченном числе исполнителей (S — 1 день, M — 2, L — 3), закрытые потоки сохраняют дату закрытия и не задерживают открытые. Этап 4 не раньше фиксации сданной версии, этап 5 после этапа 4. Показывает порядок и параллельность потоков, а не сроки. Обновление: `python3 scripts/work_packages.py project --apply --dates`. В виде Roadmap выберите поля дат вручную: Date fields → Start = Start date, End = Target date; группировка по «Этап» |
| Зависимости целиком | [plan-dependencies.md](plan-dependencies.md): слои, критический путь, что кого разблокирует |

Как изменить план: правьте таблицы в этом файле с сохранением формата, затем `python3 scripts/work_packages.py report`. CI отклонит изменение без пересчёта отчёта. Новые потоки в GitHub создаёт `python3 scripts/work_packages.py sync --apply` (повторный запуск не дублирует Issue).
