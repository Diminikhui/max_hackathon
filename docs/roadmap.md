# Дорожная карта: ядро и этапы

Документ согласует [концепт](../koncept-hackathon-max.md) с условиями кейса «Эффективный бизнес». Каждый этап — законченный продукт, который можно сдать без следующих. Дата составления: 19.09.2026; дедлайн онлайн-тура — 30.09.2026 (точное время уточнить).

## 1. Рамка

- **Видение:** единый проактивный слой между государством и бизнесом в MAX для всего российского бизнеса.
- **Название продукта:** «Пульс» ([ADR-0002](decisions/0002-team-decisions.md)).
- **Приоритетный сегмент MVP:** микробизнес и ИП с работниками без штатного бухгалтера и юриста; три ОКВЭД-направления — общепит (56), автосервис (45.2), розничная торговля (47); регионы — Москва и Республика Татарстан. Остальные отрасли и регионы — предмет масштабирования, а не MVP.
- **Основной сценарий:** ИНН → профиль → персональный перечень обязанностей с источником и датой → уведомление об изменении.
- **Граница продукта:** сообщаем о праве или обязанности, не рекомендуем действие. Автоматическая обработка помечена, рядом ссылка на первоисточник.
- **Собственный публичный API не заявляем:** баллов он не даёт, а требует OpenAPI, тестовых учёток и `DATA-API.yaml`. Внутренние методы мини-приложения описываем в OpenAPI с первого дня, чтобы при необходимости быстро заявить API (см. раздел 10).

### Принципы архитектуры

1. Каждый внешний источник — адаптер с единым контрактом и тремя реализациями: `real`, `fixture`, `synthetic`.
2. Отбор «кому и что применимо» детерминирован. Искусственный интеллект только извлекает структуру и переформулирует; система полностью работает и без него.
3. **Допустимый ИИ — только GigaChat или локальная модель.** Внешние иностранные сервисы не используются. Провайдер выбирается настройкой `LLM_PROVIDER`: `template` (по умолчанию, без ИИ) / `gigachat` / `local`. Проверяющий запускает продукт без ключей и получает рабочий результат.
4. Результат применимости: `применяется` / `не применяется` / `недостаточно данных` / `требуется проверка` / `вне покрытия`.
5. Тип факта виден всегда: официальный / заявленный / вычисленный / сценарный / модельный.
6. Тестовые и смоделированные данные явно помечены в интерфейсе, README и презентации.
7. Регион, ОКВЭД-направление и правила — подключаемые данные, а не код.
8. Компоненты общаются через порты и контракты (`contracts/`). Пока зависимость не готова, поток работает против порта и фикстуры.
9. Текст документов из внешних источников — недоверенные данные: он не может менять инструкции модели и поведение системы.

## 2. Как работать потоками

Поток (WP, work package) — независимая единица работы. Любой агент за любым участником может взять любой доступный поток. Роль «фронтенд / бэкенд» не закрепляется.

1. **Доступный поток** — тот, у которого все зависимости из колонки «Старт после» уже смержены в `main`. Порядок выбора: ⚑ критический путь → остальное `[ЯДРО]` → потоки следующих этапов.
2. **Один поток = один Issue = одна ветка = один исполнитель = один worktree.** Ветка: `<участник>/<исполнитель>/<тип>-<id>-<кратко>`, например `dima/claude/feat-k-16a-condition-evaluator`. Правила — в [TEAM_GUIDE.md](../TEAM_GUIDE.md).
3. **Зона файлов.** Поток меняет только свою зону (колонка «Зона»). Чужую зону — только через Issue её владельца или отдельный PR с пояснением.
4. **Обозначения.** ID с буквой (`K-16a`) — конкретная часть потока. ID без буквы (`K-16`) в колонке «Старт после» означает все части. `K-17*` — любое из направлений.
5. **Контракты не дробятся.** K-02 делает один исполнитель, ревьюят двое: разрез контракта между людьми даёт расхождения. После слияния K-02 каталог `contracts/` меняется только отдельным PR `contract: …` с пометкой в Issue затронутых потоков и повышением `contractVersion`.
6. **Фикстуры и миграции.** Общие данные лежат в `data/fixtures/`, миграции БД — в `packages/storage/migrations/`; каждый поток добавляет файлы только со своим префиксом `<id>-`, поэтому конфликтов слияния нет.
7. **Готовность потока** = «Готово, когда» из таблицы + Definition of Done из TEAM_GUIDE.
8. **Размер:** **S** — до полудня, **M** — около дня, **L** — два дня и более. Потоки размера L дробятся дальше, если есть независимые части.

### Предлагаемая раскладка репозитория (утверждается в K-01a)

```text
contracts/            схемы и примеры контрактов, OpenAPI мини-приложения
packages/domain/      доменная модель, порты
packages/rules/       механизм применимости
packages/adapters/    profile / requirements / opportunities: real, fixture, synthetic
packages/classifier/  провайдеры ИИ и классификатор документов
packages/storage/     схема БД, миграции, репозитории
apps/bot/             бот MAX
apps/miniapp/         мини-приложение
apps/worker/          ingest, планировщик уведомлений, отправка
data/rulepacks/       пакеты правил по направлениям и регионам
data/fixtures/        тестовые и модельные данные
docs/                 документация и решения
```

Стек по умолчанию: TypeScript, Node.js, PostgreSQL, React с MAX UI и MAX Bridge, Docker Compose. Кейс рекомендует JavaScript и React; окончательно фиксируется ADR в K-01a.

## 3. Карта зависимостей

```text
ЯДРО (этап 1)
 Волна 0  K-00  K-01a K-02  K-03a/b K-04a/b K-05a/b/c K-06a/b/c   ← все стартуют сразу
              │     │
              └──┬──┘
 Волна 1  42 потока против контрактов и фикстур                     ← K-01a + K-02, далее независимо
              │

              │
 Волна 3  K-30a/b → K-30c → K-30d ; K-31, K-33a/b/c                 ← сборка и сдача ядра
              │
 Этап 2 ──── Этап 3 ──── (сдача онлайн-этапа 30.09)
                           │
                        Этап 4 (финалисты) ──── Этап 5 (после хакатона)

Ранний старт: часть потоков этапов 2–4 не ждёт конца ядра (раздел 9).
```

**Критический путь ядра** (рассчитан по графу зависимостей, подробности — в [plan-dependencies.md](plan-dependencies.md)): K-00 → K-06a → K-17a → K-26 → K-24b → K-30b → K-30c → K-33b → K-33c. Самые длинные звенья — ручной эталонный чеклист (K-06a) и пакет правил направления A (K-17a); направления B и C идут параллельно и не блокируют сдачу ядра. Вторая ветка, сходящаяся в K-26: K-01a → K-02 → K-15 → K-16. Ветка MAX: K-05a → K-21b / K-22a → K-24 → K-30.

## 4. Этап 1. ЯДРО `[ЯДРО]`

Самодостаточный продукт: бот в MAX, который по ИНН собирает профиль, показывает персональный перечень обязанностей на выбранных направлениях и сообщает об изменениях. Запускается одной командой Docker. Работает на реальных данных там, где доступ есть, и на явно помеченных фикстурах там, где нет.

**Сдаётся:** полный работающий продукт в узком срезе (ориентир — 24.09).

**Вход:** ничего. **Параллельно с ядром** можно вести потоки раннего старта (раздел 9).

### Вопрос 1. Внутренние методы мини-приложения и «собственный API»

**Суть.** Мини-приложение в MAX — это веб-страница по HTTPS, и ей нужен наш бэкенд, чтобы получать данные. Кейс делит проверку на две ветки: для решений «с собственным API» требуются OpenAPI, тестовые учётные записи, тестовые данные и файл `DATA-API.yaml`, а платформа оценки автоматически вызывает заявленные методы. Кейс также пишет, что собственный API «не обязателен и сам по себе не даёт дополнительных баллов». Из текста неясно, считается ли обычный бэкенд мини-приложения «собственным API».

**Риск обоих ответов.** Если не заявить API, а проверяющие сочтут его собственным, мы потеряем баллы за документацию и корректность интеграции. Если заявить, а методы окажутся нестабильными, обязательные проверки не пройдут.

**Что делаем по умолчанию.** В 2-01b описываем методы мини-приложения в OpenAPI 3.1 с самого начала. Тогда при ответе «да» остаётся сделать 2-16 (один поток размера M), а при ответе «нет» файл остаётся внутренней документацией. Ничего не переделывается в обоих случаях.

**Текст вопроса организаторам:**

> Мини-приложению в MAX нужен собственный HTTPS-бэкенд для получения данных интерфейсом. Считается ли он «собственным API» в смысле раздела «Только для решений с собственным API» (OpenAPI, тестовые учётные записи, DATA-API.yaml)? Если нет, достаточно ли описать его в README как внутренний компонент решения?

### Вопрос 2. Разработка этапа 4 до объявления результатов

**Суть.** Кейс говорит: после дедлайна сданная версия кода не изменяется, а возможность вносить изменения в код и презентацию появится у финалистов после объявления результатов онлайн-этапа. Между сдачей (30.09) и результатами (около 14.10) пройдёт около двух недель. Непонятно, можно ли в это время готовить новые функции в отдельной ветке, не трогая сданную версию.

**Как читаем.** Запрещено менять сданную версию. Запрета на подготовку в стороне нигде не написано, но и разрешения нет.

**Что делаем по умолчанию.** Поток 4-00: ставим тег `online-submission` на сданный commit и не трогаем его. Всю подготовку этапа 4 ведём в отдельных ветках и в `main` сливаем только после объявления результатов. Это безопасно при любом ответе: сданная версия остаётся нетронутой. Худший исход — организаторы скажут «нельзя готовить заранее», и тогда работа этапа 4 уместится только в 15 дней после результатов.

**Текст вопроса организаторам:**

> Версия кода, сданная к дедлайну (commit hash), после него не изменяется. Можно ли до объявления результатов онлайн-этапа продолжать разработку новых функций в отдельной ветке репозитория, не меняя сданный commit, и показать их в финале, если команда пройдёт отбор?
