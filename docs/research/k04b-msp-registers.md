# K-04b: реестр МСП и реестр получателей поддержки

Проверено 25.09.2026 по официальным страницам и XSD ФНС России. Цель разведки — определить, можно ли использовать источники для построения профиля компании и поиска сведений по ИНН.

## Краткий вывод

Оба реестра опубликованы как открытые данные ФНС в виде полных ZIP-архивов с XML-файлами и XSD. Авторизация для скачивания не требуется. Документированного публичного API чтения одной записи по ИНН не найдено: API реестра получателей поддержки, упомянутое ФНС, предназначено для передачи сведений поставщиками, а СМЭВ — для межведомственного взаимодействия.

Для продукта рекомендуется:

1. Загружать новый архив по расписанию после официальной даты публикации.
2. Потоково разбирать XML и строить локальный индекс по ИНН.
3. Хранить дату среза, URL выпуска, версию XSD и контрольную сумму из HTTP-заголовка.
4. Отвечать из локального индекса; отсутствие записи трактовать как «нет в данном срезе», а не как ошибку компании.
5. Не использовать реестр получателей поддержки как каталог доступных мер: он описывает уже оказанную поддержку.

Полные архивы слишком велики для запроса на пользовательском пути: на момент проверки архив реестра МСП имел размер 2 127 751 118 байт, а архив получателей поддержки — 833 094 667 байт.

### Поля, полезные для `CompanyProfile`

| Поле XML | Назначение | Маппинг продукта |
|---|---|---|
| `ОргВклМСП/@ИННЮЛ`, `ИПВклМСП/@ИННФЛ` | ИНН ЮЛ или ИП | ключ локального индекса, `CompanyProfile.inn` |

| `СвОКВЭД/СвОКВЭДОсн/@КодОКВЭД` | основной заявительный ОКВЭД | `activity.okved_main` |
| `СвОКВЭД/СвОКВЭДДоп/@КодОКВЭД` | дополнительные заявительные ОКВЭД | `activity.okved_additional` |
| `СвОКВЭДотч/...` | ОКВЭД отчётного типа | хранить происхождение отдельно; не смешивать молча с заявительными кодами |
| `Документ/@КатСубМСП` | категория: `1` — микро-, `2` — малое, `3` — среднее предприятие | `scale.msp_category`: `micro` / `small` / `medium` |
| `Документ/@ССЧР` | среднесписочная численность | `employment.headcount`; поле необязательное |
| `СвЛиценз` | выданные лицензии | позволяет вывести `licenses.has_any`; отсутствие элемента требует аккуратной трактовки |

XSD различает заявительные сведения `СвОКВЭД` и отчётные `СвОКВЭДотч`. Для совместимости с ЕГРЮЛ/ЕГРИП в MVP следует использовать заявительный основной и дополнительные коды, а отчётные сохранять как отдельное происхождение для будущей политики разрешения конфликтов.

Важно: карточка набора предупреждает, что в выпусках с января по июнь среднесписочная численность относится к году, предшествующему предыдущему; в выпусках с июля по декабрь — к предыдущему году. Нельзя ставить срок действия `headcount` только по дате скачивания.

### Ограничение смысла данных

Запись означает, что конкретному получателю уже была оказана поддержка. Она не доказывает, что такая мера сейчас открыта, что компания снова подходит под условия или что приём заявок продолжается. Поэтому этот реестр полезен для истории и аналитики, но не заменяет `OpportunitySource` и каталог актуальных мер поддержки.

ФНС отдельно указывает, что при прекращении деятельности получателя сведения об оказанной поддержке из реестра не исключаются. Наличие записи также не подтверждает текущий статус организации.

## Правовой режим и безопасность

Обе карточки ссылаются на [типовые условия использования открытых данных](https://www.nalog.gov.ru/files/tipovye_usloviya_od.pdf). Они допускают коммерческое и некоммерческое использование без отдельного договора или лицензии, но требуют законной цели, ссылки на источник и достоверного воспроизведения.

Несмотря на открытый режим, выгрузки содержат ФИО и ИНН индивидуальных предпринимателей и физических лиц на НПД. Для продукта:

- не коммитить реальные записи и не логировать ФИО/ИНН;
- хранить только минимально необходимые поля;
- отделять сырую зону импорта от прикладного профиля;
- указывать ФНС и URL выпуска в `SourceRef`;
- явно помечать приложенные образцы как модельные.

## Рекомендуемый контур загрузки

```text
карточка open data → URL нового ZIP → проверка размера/sha256
                    → потоковый unzip/XML parse
                    → нормализация + provenance
                    → локальный индекс по ИНН
                    → ProfileSource / история поддержки
```

Практические правила:

- проверять `ETag`, `Last-Modified` или имя выпуска до скачивания;
- сверять `x-amz-meta-sha256`, если заголовок доступен;
- ограничивать максимальный размер и свободное место до загрузки;
- не распаковывать архив целиком, XML обрабатывать потоком;
- валидировать версию `ВерсФорм` и поддерживаемую XSD;
- публиковать новый индекс атомарно только после полного успешного импорта;
- сохранять предыдущий пригодный индекс при сетевой или форматной ошибке;
- не опрашивать источник чаще официального графика без отдельной причины.

## Решение для MVP

| Источник | Решение |
|---|---|
| Реестр МСП | Использовать как официальный источник категории МСП, региона, ОКВЭД, численности и наличия лицензий через локальный индекс ежемесячного среза. |
| Реестр получателей поддержки | Не включать в обязательный путь профиля. Подготовить тот же механизм офлайн-индекса для истории поддержки; не использовать как источник актуальных возможностей. |
| Интерактивный поиск ФНС | По умолчанию — только ручная проверка и ссылка пользователю. Автоматизация `search-proc.json` возможна лишь по решению команды (см. «Два варианта получения профиля»). |
| СМЭВ и API поставщика | Не использовать в MVP без отдельного доступа и соглашения; это не публичный read-API продукта. |

## Два варианта получения профиля: решение команды

Команда 23.09.2026 проверила второй путь ([предложение, раздел 5](../proposals/2026-09-23-gaps-and-proposals.md)). Выбор между вариантами — решение человека (K-00 / K-12b), а не агента.

| | A. Офлайн-импорт ежемесячного среза | B. `POST https://rmsp.nalog.ru/search-proc.json` (`mode=quick`, `query=<ИНН>`) |
|---|---|---|
| Статус источника | официальный набор открытых данных ФНС | внутренний endpoint публичного веб-сервиса ФНС, без опубликованной спецификации |
| Поля | все поля XSD (категория, регион, ОКВЭД, ССЧР, лицензии, история) | `inn`, `ogrn`, `okved1`, `regioncode`, `category`, `od2_sschr`, `has_licenses`, `isnew` — достаточно для условий MVP |
| Актуальность | срез раз в месяц (10-е число) | на момент запроса |
| Стоимость реализации | ZIP ~2,13 ГБ, потоковый XML-парсер, хранилище и индекс по ИНН; до сдачи 29.09 рискованно | один HTTP-запрос на пользователя; адаптер за часы |
| Риски | объём и время импорта; отставание до месяца | ограничение кейса о «частных API»; формат может измениться без уведомления; возможны лимиты и защита от ботов |
| Деградация | индекс остаётся доступен при сбое сети | при недоступности — только заявленные факты или fixture |

**Вывод разведки.** Для промышленного контура рекомендуем вариант A. Для демо до сдачи реалистичен только B — при условии, что команда явно принимает риск внутреннего endpoint, помечает его в интерфейсе как источник ФНС с датой получения и держит fixture-адаптер как запасной путь. Без такого решения MVP работает на fixture и заявленных фактах.
