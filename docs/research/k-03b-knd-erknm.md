# K-03b. КНД и ЕРКНМ: доступ, форматы и пригодность для интеграции

Проверено 25.09.2026. Цель — определить, можно ли использовать публичные ресурсы КНД, ЕРВК и ФГИС ЕРКНМ как `RequirementSource` для автоматического расчёта обязанностей компании.

## Вывод

**Для `RequirementSource` K-13c пока нужна явно модельная fixture-реализация.** Публичные данные ЕРКНМ доступны без авторизации в виде больших XML-выгрузок и через поиск на портале. Однако ЕРКНМ учитывает уже назначенные и проведённые контрольные, профилактические и иные мероприятия. Это не нормативный каталог обязанностей, применимых к произвольной компании.

ЕРВК содержит виды контроля и нормативные акты, но публичная карточка зависит от выбранного региона, а официальный поддерживаемый API или массовая выгрузка не найдены. XLSX на портале КНД содержит агрегированную статистику, а не записи требований или проверочных листов. Интеграция ЕРКНМ через СМЭВ предусмотрена для подключённых государственных информационных систем и не является открытым API для хакатонного приложения.

Следствие для архитектуры:

- ФГИС РОТ и проверенные вручную пакеты правил остаются источниками применимых обязанностей.
- ЕРВК может служить справочником видов контроля и нормативных актов после подтверждения способа доступа.
- ЕРКНМ следует рассматривать как отдельный источник истории и статусов проверок, а не как `RequirementSource`.
- До появления разрешённого и документированного интерфейса K-13c не должен обращаться к внутренним HTTP-маршрутам публичных сайтов.

## Риски данных и эксплуатации

1. Открытая выгрузка ЕРКНМ содержит реальные ИНН, ОГРН, названия, ФИО инспекторов и потенциально СНИЛС. Не сохранять исходные записи в репозитории, тестовых логах и fixtures.
2. Один месяц публикуется повторными снимками. Имя файла и дата публикации не заменяют устойчивый ключ мероприятия; дедупликацию нужно строить по `ERPID` и версии/дате получения.
3. XSD имеет дату в имени, но это не гарантия неизменности семантики справочников. Значения `DICT_ID`, `DICT_VERSION_ID`, `GUID` и текст нужно хранить вместе.
4. Поиск портала защищён CAPTCHA. Автоматизация CAPTCHA и вызов внутренних маршрутов в обход штатного UI не допускаются.
5. ЕРКНМ показывает, что произошло с конкретным контролируемым лицом. Вывод «требование применимо» по совпадению ОКВЭД другой компании был бы юридически ненадёжным.
6. Реальные данные из выгрузки нельзя использовать как демонстрационные. Для демо нужен отдельный синтетический набор с явной пометкой «модельные данные».

## Образцы для зависимых потоков

- [`k03b-erknm-observation.json`](../../data/fixtures/k03b-erknm-observation.json) — воспроизводимые метаданные проверки без записей компаний и персональных данных.
- [`k03b-model-erknm-records.json`](../../data/fixtures/k03b-model-erknm-records.json) — два полностью модельных события в подмножестве полей XSD. Это не ответ API и не юридическое основание.

Файлы не вводят новый контракт. Они нужны K-13c для оценки маппинга и для отрицательного теста: запись ЕРКНМ нельзя автоматически преобразовать в `Requirement` без независимо подтверждённого основания и условия применимости.

## Рекомендация для K-13c

1. Реализовать fixture-источник с `info.isModel = true`; в интерфейсе явно писать «модельные данные».
2. Не называть адаптер ЕРКНМ реализацией `RequirementSource`. Если границы потока требуют этот порт, вернуть `out_of_coverage` или пустой набор с диагностикой «источник не является каталогом требований».
3. Вынести будущую интеграцию ЕРКНМ в отдельный порт истории контроля, например `InspectionHistorySource`, отдельным запросом изменения контракта.
4. Для будущего пакетного контура получать метаданные, скачивать только новый снимок, проверять XSD и размер, разбирать XML потоково, удалять персональные поля до хранения и дедуплицировать по `ERPID`.
5. Для real перейти к разработке только после подтверждения оператором разрешённого интерфейса, лимитов, прав повторного использования и состава публичных данных.

## Ограничения исследования

- Полный ZIP на 223,7 МБ не скачивался: структура проверена по официальной XSD и метаданным, чтобы не переносить реальные данные компаний.
- Закрытая часть, СМЭВ и кабинеты участников не проверялись, потому что у проекта нет соответствующих полномочий и тестового контура.
- Отсутствие найденной документации API не доказывает, что интерфейса нет у оператора. Оно означает, что до официального подтверждения нельзя строить на нём MVP.
