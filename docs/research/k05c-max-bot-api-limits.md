# MAX Bot API: лимиты, клиенты и контуры

- Дата проверки: 2026-09-25
- Область: MAX Bot API и MAX Bridge
- Источники: публичная документация MAX и официальный OpenAPI-репозиторий
- Уровень уверенности: числа ниже подтверждены документацией; нагрузочное тестирование с токеном не проводилось

## Короткий вывод

Для текущей реализации нужно считать `https://platform-api2.max.ru` каноническим API URL, ограничивать суммарный исходящий поток до 30 запросов/с и отдельно — отправку до 2 сообщений/с в один диалог, группу или канал. Для production MAX требует Webhook; Long Polling оставлен для разработки и тестов. Webhook должен быстро фиксировать событие и отвечать `200`, а фактическую обработку выполнять асинхронно.

Название `platform-api2` больше нельзя трактовать как доказательство отдельного хакатонного API. На дату проверки официальный портал и OpenAPI-схема сами используют этот домен. Документированных различий его протокола с `platform-api.max.ru` не найдено. Известное отличие окружения команды — выданный организаторами бот и необходимость доверять корневому сертификату НУЦ Минцифры — остаётся, но это не подтверждает наличие особого набора методов или лимитов.

## Подтверждённые числовые лимиты

| Область | Лимит | Практическое следствие |
| --- | ---: | --- |
| Все запросы к `platform-api2.max.ru` | 30 запросов/с | Общий limiter на один токен/интеграцию; оставить запас для служебных запросов |
| Отправка в один диалог, группу или канал | 2 сообщения/с | Отдельная FIFO-очередь на `chat_id`; превышение MAX рекомендует сглаживать задержкой |
| Текст сообщения | 4 000 символов | Длинный ответ делить по смысловым блокам до постановки в очередь |
| Long Polling: `limit` | 1–1 000, по умолчанию 100 | Не ожидать более 1 000 updates за ответ |
| Long Polling: `timeout` | 0–90 с, по умолчанию 30 с | Таймаут HTTP-клиента должен быть больше заданного polling timeout |
| Webhook: ожидание ответа | 30 с | Сначала сохранить/поставить update в очередь, затем вернуть `200` |
| Webhook: повторы | до 10 | Обработчик обязан быть идемпотентным |
| Первый повтор Webhook | через 60 с | Не полагаться на мгновенный повтор |
| Рост интервала повторов | ×2,5: 60, 150, 375 с, … | Возможны поздние дубликаты и перестановка событий |
| Автоотписка Webhook | после 8 ч без успешного ответа | Нужны alert и периодическая проверка подписки |
| Webhook secret | 5–256 символов | Проверять `X-Max-Bot-Api-Secret`; допустимый шаблон в схеме — `[A-Za-z0-9_-]` |
| Webhook transport | HTTPS, только порт 443 | Нельзя указывать нестандартный внешний порт; нужна полная доверенная цепочка TLS |
| Inline keyboard | 210 кнопок, 30 рядов, 7 кнопок в ряду | Валидировать клавиатуру до вызова API |
| Крупные кнопки | 3 в ряду | Относится к `link`, `open_app`, `request_geo_location`, `request_contact` |
| Изображение | до 50 МБ и до 7 680 × 7 680 px | Проверять и размер файла, и геометрию |
| Видео | до 250 МБ | Загружать через URL, полученный от `POST /uploads` |
| Аудио | до 256 МБ и до 60 минут | Проверять оба ограничения |
| Файл | до 4 ГБ | Не смешивать самостоятельный file attachment с image/video |
| Медиа в сообщении | до 12 вложений | Документированы комбинации: 12 image, 12 video либо 6 image + 6 video; клавиатура занимает отдельное вложение |
| Mini App URL | до 1 024 символов, только HTTPS | URL задаётся в настройках бота; пробелы не поддерживаются |
| `startapp` payload | до 512 символов | Разрешены только `A-Z`, `a-z`, `0-9`, `_`, `-`; иначе payload удаляется из URL-ответа |
| `downloadFile` ожидание native-клиента | 60 с | Обрабатывать `client.download_file.request_timeout` |

Источники чисел: [обзор API](https://dev.max.ru/docs-api), [отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages), [Long Polling](https://dev.max.ru/docs-api/methods/GET/updates), [Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions), [клавиатура](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard), [медиафайлы](https://dev.max.ru/docs-api/use-cases/sending-messages/media), [загрузка](https://dev.max.ru/docs-api/methods/POST/uploads), [подключение мини-приложения](https://dev.max.ru/docs/webapps/introduction), [MAX Bridge](https://dev.max.ru/docs/webapps/bridge).

### Что не удалось подтвердить числом

Документация говорит, что Long Polling ограничен «по скорости и сроку хранения событий», но не публикует конкретные значения. Их нельзя подменять предположением. Если это станет критично, значения нужно измерять на выданном боте и считать свойством текущего окружения, а не публичным контрактом.

Для ответа `429` в открытой документации не описаны единый формат `Retry-After`, точный алгоритм quota window или область общей квоты — токен, бот, IP либо иной ключ. Реализация должна уважать `Retry-After`, если заголовок пришёл, а иначе применять exponential backoff с jitter и ограничением числа попыток.

## Получение событий

### Webhook — production-вариант

`POST /subscriptions` включает push-доставку и одновременно отключает Long Polling. Endpoint должен:

1. быть доступен по HTTPS на внешнем порту 443;
2. иметь сертификат доверенного УЦ (включая НУЦ Минцифры), совпадающие CN/SAN и полную цепочку;
3. проверить `X-Max-Bot-Api-Secret`, если secret задан;
4. дедуплицировать событие и безопасно поставить его в обработку;
5. вернуть `200 OK` не позднее 30 секунд.

Любой другой статус или таймаут считается неуспешной доставкой. MAX выполняет до десяти повторов с растущим интервалом и автоматически удаляет подписку после восьми часов без успешного ответа. Поэтому тяжёлая бизнес-логика до ответа — риск потери подписки.

### Long Polling — только разработка и тесты

`GET /updates` работает, только когда Webhook-подписки нет. `marker` из ответа указывает следующую позицию; после передачи marker предыдущие события считаются прочитанными. Без marker (или с `null`) API возвращает только последнее обновление, поэтому первый запрос способен пропустить накопленную историю.

Два процесса с одним токеном нельзя считать независимыми потребителями. Активный Webhook полностью выключает polling, а несколько polling-процессов разделяют продвижение marker на уровне клиентов без документированных consumer groups. Для демонстрации должен быть ровно один владелец приёма событий либо отдельный бот/токен.

## Отправка, вложения и обработка ошибок

- Авторизация передаётся только заголовком `Authorization: <access_token>`. Query-параметр токена больше не поддерживается.
- У API документированы коды `200`, `400`, `401`, `404`, `405`, `429`, `503`; отдельные методы также описывают `500`. Повторять автоматически следует только временные ошибки и только для идемпотентной операции либо с собственной защитой от дублей.
- После загрузки медиа сервер обрабатывает файл асинхронно. Немедленная отправка может вернуть `attachment.not.ready`; нужна ограниченная повторная попытка с задержкой.
- Тип attachment `photo` устарел и не поддерживается; используется `image`.
- URL загрузки предназначен для одного файла. Документация указывает неограниченный срок его действия, но безопаснее получать URL непосредственно перед загрузкой и не сохранять его как постоянный контракт.
- Самостоятельное вложение `file` можно отправить вместе с одной клавиатурой, но не вместе с image/video. Пересланные сообщения не сохраняют кнопки.
- Для канала `notify=false` неприменим: уведомление должно быть `true` либо параметр следует опустить.

Рекомендуемая схема limiter для задачи 3-05: глобальный token bucket не более 30 rps, per-chat очередь не более 2 msg/s, резерв ёмкости для `/uploads`, callbacks и служебных запросов, backoff с jitter на `429`/`503`, метрики глубины очереди и возраста самого старого сообщения.

## Поведение в web, desktop и mobile

MAX описывает Mini App как одну web-кодовую базу, но MAX Bridge явно сообщает платформу: `ios`, `android`, `desktop` или `web`. Значит, адаптацию следует строить по `window.WebApp.platform` и capability checks, а не по user-agent.

Подтверждённые различия:

| Возможность | iOS / Android | Desktop | Web |
| --- | --- | --- | --- |
| `shareContent` — системный экран шеринга | Да | Не заявлено | Нет |
| `downloadFile` через Bridge | Внутри клиента, HTTPS и только после клика | Внутри клиента, HTTPS и только после клика | Нет |
| `DeviceStorage` | Да | Документация не выделяет ограничение | Нет |
| `HapticFeedback` | Да, при поддержке устройства | Нет | Нет |
| NFC | Только Android | Нет | Нет |
| `getLaunchContext` | Android ≥ 26.19.2; iOS ≥ 26.20.0 | Не заявлено | Не заявлено |

Общие ограничения Bridge:

- `openLink`, `openMaxLink`, скачивание и внутренний шеринг требуют реального пользовательского клика;
- `downloadFile` принимает только HTTPS и не поддерживает скачивание через обычный `href`;
- одновременно открыто только одно мини-приложение: запуск нового закрывает текущее;
- `initDataUnsafe` нельзя использовать как доказательство подлинности; сервер должен валидировать строку `initData`;
- viewport следует получать через `getViewportSize`, а тему, back button и close behavior — синхронизировать через Bridge.

Документация не даёт полной матрицы методов по версиям всех четырёх клиентов. До релиза обязательна ручная проверка минимум на актуальных Android, iOS, desktop и web:

1. запуск из кнопки бота и прямого `?startapp` deep link;
2. валидация init data и передача payload на кириллице/границе 512 символов;
3. back/close, клавиатура, изменение viewport и тёмная тема;
4. открытие внешней ссылки и MAX deep link;
5. скачивание файла, внутренний и системный share;
6. повторный запуск Mini App и восстановление состояния;
7. деградация каждого Bridge-метода при отсутствии capability.

## `platform-api2` и актуальность документов

### Подтверждено сейчас

- Главная страница Bot API, страницы методов, руководство по созданию бота и официальная [OpenAPI-схема версии 0.0.32 от 2026-07-01](https://github.com/max-messenger-bot/max-bot-api-schemas/blob/main/schema_2026_07_01.json) используют `https://platform-api2.max.ru`.
- Документация прямо просит направлять запросы на `platform-api2.max.ru` вместо `platform-api.max.ru` и добавить сертификат Минцифры в доверенные.
- Использовать `-k`, `verify=false` или глобально отключать TLS нельзя. Решение проекта с `NODE_EXTRA_CA_CERTS` согласуется с требованиями MAX.

### Расхождения с репозиторием и старыми примерами

1. [ADR-0003](../decisions/0003-issued-bot-and-hackathon-contour.md) и roadmap говорят, что документация описывает `platform-api.max.ru`, а `platform-api2` — отдельный хакатонный контур. На 2026-09-25 это уже неверно: текущая официальная документация указывает `platform-api2` как рабочий домен для всех интеграций.
2. Поэтому сравнить «хакатонный» и «боевой» протоколы по опубликованным контрактам невозможно: второй домен больше не представлен как канонический API. Сохранять configurable `MAX_API_BASE_URL` всё равно правильно.
3. Старые примеры с `access_token` в query противоречат текущему требованию заголовка `Authorization` и не должны копироваться.
4. Старый тип вложения `photo` заменён на `image`.
5. Некоторые страницы ещё описывают Long Polling как удобный путь разработки, но актуальная страница метода формулирует жёстче: для production использовать только Webhook и рекомендует Webhook на всех этапах.

ADR не изменён в этой задаче из-за зоны файлов `docs/research/`. Владельцу архитектурных решений следует отдельным PR уточнить исторический контекст: организаторы действительно выдали бота и сообщили этот endpoint, но сам endpoint теперь публично документирован как основной.

## Решения для зависимых потоков

- **K-05a:** брать base URL из `MAX_API_BASE_URL`, по умолчанию `https://platform-api2.max.ru`; авторизация только заголовком; TLS проверять с локально подключённым корнем НУЦ Минцифры; Webhook считать целевым режимом.
- **K-21b / K-22a:** текст до 4 000 символов, клавиатура до 210 кнопок и ограничения по типам крупных кнопок; обязательно проверить рендеринг и callback на mobile и web.
- **3-05:** реализовать двухуровневый limiter 30 rps global + 2 msg/s per chat, backoff на временные ошибки и наблюдаемую очередь.
- **Demo/QA:** не запускать production Webhook и локальный polling на одном токене; перед демонстрацией проверять активную подписку и единственного владельца consumer loop.

## Что остаётся проверить с доступом к токену

Ни один из пунктов ниже нельзя безопасно вывести из публичной документации:

- является ли 30 rps квотой на токен, бота, IP или инфраструктурный tenant;
- возвращает ли `429` стабильный `Retry-After` и в каких единицах;
- фактическая глубина и срок хранения Long Polling;
- порядок и дедупликационный идентификатор событий при webhook retry;
- одинаковы ли лимиты выданного бота и самостоятельно созданного бота;
- какие Bridge capabilities доступны в конкретных версиях клиентов проверяющих.

Проверять это следует отдельным безопасным smoke/load-тестом с согласованным окном, без публикации токена и без превышения документированных 30 rps.
