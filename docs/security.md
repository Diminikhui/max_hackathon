# Безопасность репозитория

Этот документ фиксирует обязательные меры для кода и CI. Проверки выполняются в workflow `Repository checks` для каждого Pull Request и push в `main`.

## Секреты

- Токены, пароли, ключи API, приватные ключи и реальные данные компаний не коммитятся.
- Локальные значения хранятся в игнорируемом `.env`; в репозитории остаётся только `.env.example` с пустыми или явно модельными значениями.
- В CI секреты задаются через GitHub Actions Secrets и не печатаются в логи.
- Gitleaks проверяет историю Git в CI. Если секрет попал в commit, его нужно сначала отозвать/ротировать, а затем удалить из истории. Простого удаления из последующего commit недостаточно.

Ложное срабатывание не исправляют подменой сканера или глобальным исключением. Нужно убедиться, что это тестовое значение, и добавить точечное исключение с обоснованием в отдельном PR.

## Зависимости и лицензии

- Node.js и pnpm зафиксированы через `.nvmrc` и `packageManager`.
- Точное дерево пакетов хранит `pnpm-lock.yaml`; CI устанавливает его только с `--frozen-lockfile`. Изменение manifest без обновлённого lockfile ломает CI.
- Внешние GitHub Actions зафиксированы на неизменяемые commit SHA. При обновлении рядом с SHA сохраняют комментарий с major-версией.
- CI строит полный отчёт `pnpm licenses list --json`. Разрешены только явно проверенные permissive лицензии и MPL-2.0. Новый тип лицензии останавливает CI и требует ручного разбора. Лицензию добавляют в allowlist только вместе с обоснованием в PR.

## TLS

Проверку TLS нельзя отключать ни в коде, ни в скриптах, ни в CI. Для контура MAX корневой сертификат НУЦ Минцифры подключается только к процессу приложения через `NODE_EXTRA_CA_CERTS`; см. [ADR-0003](decisions/0003-issued-bot-and-hackathon-contour.md) и [инструкцию по сертификату](../certs/README.md).

CI блокирует типовые обходы для Node.js, Python, Go, curl и wget. Markdown и сам workflow сканера исключены, потому что они содержат описания самих запретов. Остальные workflow сканируются. Если сканер не узнаёт новую технологию, её шаблон добавляют в эту проверку, а не в список исключений.

## Безопасность данных (K-32b)

Код — пакет `@max-hackathon/security` (`packages/security/`), проверки — `pnpm --filter @max-hackathon/security test`. Все тестовые данные модельные.

### Проверка `initData`

- Мини-приложение передаёт серверу строку `initData`; сервер проверяет её функцией `verifyInitData(initData, MAX_BOT_TOKEN)`. Алгоритм — HMAC-SHA256 по токену бота (см. [K-05b](research/k05b-max-miniapp-launch.md)), сравнение подписи за постоянное время.
- Срок жизни — не больше часа (`DEFAULT_INIT_DATA_MAX_AGE_SEC`, рекомендация MAX), `auth_date` из будущего допускается только в пределах 60 секунд расхождения часов.
- Отклоняются: пустая и слишком длинная строка (больше 8 КБ), битое кодирование, повтор параметра, отсутствие `hash`, `auth_date` или пользователя с числовым `id`, `start_param` не по формату MAX.
- Клиенту при любой ошибке отвечаем одинаково (`UNAUTHENTICATED`, 401), код причины (`InitDataError.code`) — только в лог. Сообщения ошибок не содержат значений из `initData`.
- `initDataUnsafe` на клиенте — только для отображения; личность пользователя берётся исключительно из результата серверной проверки.
- Реальный `MAX_BOT_TOKEN` в тестах не используется: строки подписывает `signInitDataForTest` с модельным токеном.

### Минимизация персональных данных

| Данные | Что храним | Что не храним |
|---|---|---|
| `initData` | только `maxUserId`, `start_param`, `chat.id`, язык | строку `initData`, имя, фамилию, `username`, фото |
| Пользователь и чат MAX | id для связи с профилем и отправки | — |
| Профиль ИП | ИНН и ФИО (это ПДн), факты, заявленные ответы | — |
| Deep link (`start_param`) | непрозрачный токен | ИНН, ОГРН, телефон и другие номера: проверка `isSafeStartParam` |

- `verifyInitData` возвращает минимальный набор полей: имя, `username` и фото пользователя сервису не нужны и дальше проверки не проходят.
- В логах, метриках и аналитике вместо id пользователя и чата — псевдоним `pseudonymize(value, key, purpose)` (HMAC-SHA256 с секретным ключом не короче 32 символов; разные `purpose` дают несопоставимые псевдонимы). Простой хеш без ключа не годится: id и ИНН перебираются. Переменную окружения для ключа заводит поток, который первым пишет такие логи (2-01b), и документирует её в `.env.example`.
- В интерфейсе и поддержке ИНН показывается маской `maskInn` (`77******16`).
- ИНН из 12 цифр (`isPersonalInn`) — ИНН физического лица: профиль ИП целиком относится к ПДн. Хранение — на серверах в России (гипотеза из [roadmap](roadmap.md), до юридической проверки — российский хостинг).

### ПДн не попадают в логи

- Логгер `@max-hackathon/observability` маскирует секреты и ПДн по ключам (`inn`, `init_data`, `user_id`, `chat_id`, `full_name`, `first_name`, …) и по содержимому строк (email, телефон, номера из 10–15 цифр, токены).
- **Ограничение:** `displayName` и `username` логгер не маскирует, а у ИП `displayName` — это ФИО. Поэтому профиль в лог передаётся только через `toLogSafeProfile(profile)` (id, тип, модельность, число фактов), а данные пользователя MAX — только после `verifyInitData` или как псевдоним.
- Тест `packages/security/test/pii.test.ts` прогоняет через настоящий логгер `initData`, результат проверки, псевдоним и профиль ИП и проверяет, что в записи нет id, имени, `username`, ИНН и ФИО. Он же фиксирует ограничение с `displayName`: если логгер начнёт его маскировать, тест нужно обновить.

### Сроки хранения

Сроки — `RETENTION_POLICY` в `packages/security/src/retention.ts`; `retentionCutoff` и `isRetentionExpired` дают границу удаления. Удаление выполняют владельцы хранилищ (`packages/storage`, `apps/worker`) по этим константам.

| Категория | Срок | Отсчёт | Основание |
|---|---|---|---|
| `init_data` | не хранится | — | после проверки подписи нужен только id |
| `session` | 1 час | создание | не дольше срока `initData` |
| `profile` | 180 дней | последняя активность | профиль, факты и ответы нужны, пока пользователь получает уведомления |
| `user_binding` | 180 дней | последняя активность | удаляется вместе с профилем |
| `notification` | 90 дней | отправка | дедупликация и разбор жалоб |
| `change_event` | 365 дней | создание | события изменений без ПДн, история расчётов |
| `application_log` | 14 дней | создание | разбор инцидентов, логи без ПДн |

По запросу пользователя профиль, факты, связи и уведомления удаляются сразу, не дожидаясь срока. Сроки — решение для MVP; при юридической проверке хранения ПДн их пересматривают.

### Доступ к данным

- Субъект запроса — `maxUserId` из проверенного `initData` или серверной сессии, никогда не из тела или параметров запроса.
- Пользователь видит и меняет только профили, привязанные к нему (`canAccessCompany`, `assertCompanyAccess`). Отказ (`AccessDeniedError`) отдаётся клиенту как «не найдено» (404), чтобы по ответу нельзя было узнать о существовании чужого профиля.
- Модельные профили из `data/fixtures/` — демонстрационные и ПДн не содержат.
- Доступ к БД и логам на сервере — только у участников команды, отвечающих за развёртывание; выгрузки с ПДн из рабочей БД в репозиторий, Issue и чаты запрещены.

## Локальная проверка

```bash
pnpm install --frozen-lockfile
pnpm licenses list --json
./scripts/verify-repository.sh
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

После изменения security workflow нужно также проверить сам YAML и дождаться всех job в Pull Request.
