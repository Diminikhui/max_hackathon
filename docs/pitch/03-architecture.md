## Слайд 10. Архитектура

**Один процесс держит бота и уведомления; применимость считает детерминированный движок**

```text
                         ┌──────────────── процесс «Пульса» (контейнер worker) ────────────────┐
MAX ──webhook──► бот: онбординг · перечень · уточнения · настройки · 🧪 демо-кнопка           │
                  │                                                                              │
                  ▼                                                                              │
     сервисы профиля и перечня ──► движок применимости (5 статусов, объяснение, первоисточник) │
                  │                           ▲                                                  │
                  ▼                           │ пакеты правил (JSON, версии, проверены человеком)│
             PostgreSQL ◄── новая версия пакета ──► пересчёт ──► очередь ──► MAX Bot API ──────►│ пользователь
                  ▲                                                                              │
     реестр МСП ФНС (профиль по ИНН)                                                             │
                         └───────────────────────────────────────────────────────────────────────┘
VPS: Nginx (TLS, 443) → webhook и мини-приложение; база наружу не публикуется; резервные копии и мониторинг
```

Ключевые решения:

1. **Правила — это данные.** Регион и отрасль подключаются новым пакетом правил, а не правкой кода. Пакет проходит валидатор до публикации.
2. **Применимость определяет не ИИ.** Условия пакета вычисляются детерминированно над фактами профиля. ИИ (только GigaChat или локальная модель) допускается лишь для классификации документов ленты и черновиков записей. Без ключей продукт работает в режиме `LLM_PROVIDER=template`.
3. **Модельное отделено от реального в коде.** Модельные ИНН берут профиль из фикстуры, остальные — из реестра МСП. Модельные пакеты видят только модельные компании.
4. **Состояние — в PostgreSQL.** Диалог, привязка чата к компании, настройки и очередь уведомлений переживают перезапуск.

Стек: TypeScript, Node.js 24, pnpm workspace, PostgreSQL, Docker Compose; мини-приложение — React, MAX UI и MAX Bridge.

## Слайд 11. Данные и интеграции

**Что реально, что модельное, что целевое — по состоянию сдаваемой версии**

| Интеграция или данные | Для чего | Состояние |
|---|---|---|
| MAX Bot API | приём событий, ответы и уведомления | **Реальная**: бот, выданный организаторами, хакатонный контур `platform-api2.max.ru`. Боевой прогон на web и mobile — K-30d |
| Реестр МСП ФНС (`rmsp.nalog.ru`) | профиль по ИНН: ОКВЭД, регион, категория, численность | **Реальная**: внутренний интерфейс страницы поиска без официальной спецификации |
| ЕГРЮЛ/ЕГРИП | запасной источник профиля | Адаптер написан (K-12a), в сборку процесса **не подключён** |
| Пакет правил общепита: федеральный + Татарстан | перечень обязанностей | **Реальные данные**: 21 + 2 записи, собраны и проверены вручную по официальным актам |
| Пакет автосервиса | перенос на второе направление | **Реальные данные**, тонкий пакет: 7 записей, все с неполным покрытием |
| Модельные компании K-28 и пакет `k28-model` | демонстрация и тесты | **Модельные**: 5 вымышленных ИНН с верной контрольной суммой; помечены в данных и в сообщениях |
| Демо-изменение K-29 (`k28-model` v1 → v2) | показ уведомления без ожидания реального изменения закона | **Модельное**: кнопка «🧪 Показать пример изменения (модельное)» |
| Лента regulation.gov.ru | ранний сигнал о проектах актов | Загрузчик и отбор написаны (K-18a–K-18c), в сдаваемой сборке **не запускается** |
| GigaChat | классификация документов ленты | Провайдер написан (K-19b), для классификации в сборку процесса **не подключён**; пересказ «Простым языком» использует его за флагом `BOT_FEATURES=explain` (по умолчанию выключен); по умолчанию `template` без ключей |
| Мини-приложение MAX | подробности и настройки | Каркас с MAX UI и Bridge, экраны — заглушки; вне MAX показывает плашку «Модельный режим». API мини-приложения пуст |
| ЕСИА, ведомственные ГИС, Госключ, МСП.РФ | подтверждённая роль организации, заявки, подпись, меры поддержки | **Целевые**: условия подключения описаны в матрице интеграций, в сдаваемой версии их нет |

**Как читать.** Строки сверены с `main` и сценарием K-33b на 29.09.2026. MAX Bot API подтверждён боевым прогоном K-30d в web и mobile на SHA `7fbaef7`; дополнительная проверка показала три одинаковых ответа бота на три быстрых нажатия одной кнопки (исправление — PR #349). Перед экспортом нужно повторить сценарий на финальном сдаваемом SHA. Модельную строку нельзя называть рабочей интеграцией.

Правило модельности: модельны **входные** данные и события, а движок применимости, версии пакетов, объяснение, дедупликация и отправка проходят тот же код, что и для реального источника. Поэтому демо проверяет механику продукта, но не доступ к ведомственным системам.

## Слайд 12. Ограничения и риски

**Честные границы MVP и что делаем при сбое**

**Деградация: что происходит, когда источник недоступен**

| Сбой | Поведение |
|---|---|
| Реестр МСП не отвечает или сменил формат | «Не удалось получить данные» и предложение повторить; сценарий не ломается |
| Нет данных для условия записи | Статус «недостаточно данных» и уточняющий вопрос вместо догадки |
| Компания вне проверенного региона или направления | Федеральная часть перечня и строка «вне покрытия» |
| Нет ключа GigaChat | Режим `template`: детерминированный результат без ИИ |
| MAX ограничивает частоту | Очередь с лимитами платформы (30 запросов/с на бота, 2 сообщения/с в чат) и повторами |

**Ограничения MVP** [факт]

- Охват: общепит в Москве и Татарстане, федеральный пакет возможностей для общепита и тонкий пакет автосервиса.
- Профиль берётся из неофициального интерфейса реестра МСП; в реестре только субъекты МСП, данные — срез на 10-е число месяца. Дополнительные ОКВЭД и отсутствие работников бот уточняет у пользователя.
- ИНН не подтверждает право действовать от имени компании, поэтому показываются только общедоступные сведения и расчёт по ним.
- Один VPS без резервирования; резервные копии хранятся на нём же.
- Ранние сигналы, ежемесячная сводка и лента regulation.gov.ru написаны, но в сдаваемой сборке не запускаются: до сдачи реальные пакеты не меняются, изменение показывается демо-кнопкой.
- В ручной проверке K-30d одно сообщение пришло три раза из-за трёх быстрых нажатий одной кнопки; очередь отправки дублей не давала (дедупликация по ключу проверена сквозными тестами). Исправление — PR #349, повторная проверка в MAX нужна на новой версии.
- Нагрузочная, юридическая и длительная эксплуатационная проверка не проводились.

**Главные риски**

| Риск | Что снижает |
|---|---|
| Ошибочная применимость или пропуск обязанности | Узкое проверенное покрытие; два человека сверяют запись с первоисточником; ссылка на основание в каждой карточке; остановка рассылки при ложном точном уведомлении |
| Пакет правил устаревает | Срок действия пакета, дата актуальности, процесс обновления с подтверждением человеком (3-08d) |
| Неофициальный интерфейс реестра МСП изменится | Адаптер изолирован и отвечает «источник недоступен»; запасной ЕГРЮЛ; ответ пользователя как заявленный факт |
| Зависимость от платформы MAX и сертификата НУЦ Минцифры | Транспорт отделён от доменной логики; сертификат подключается только процессу приложения, проверка TLS не отключается |
| Шум уведомлений — пользователь отключает бота | Редкие дельты, настройки, главная метрика пилота — доля отключивших |
| Утечка секретов или персональных данных | Секреты только в окружении сервера; в логах нет токенов, ИНН, телефонов и идентификаторов; проверка подписи `initData` мини-приложения реализована в пакете безопасности |
